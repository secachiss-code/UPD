# Баглист статического аудита

Проверены исходники, генерация systemd unit-файлов и документация. Выполнено шесть проходов: два по исходным 19 пунктам (локальное условие/факт и сквозной путь вызова/эффект), два на поиск новых дефектов (границы ресурсов и доверия; состояния TUI, гонки и отказ фоновых задач), два на формализацию (разделение фактов и ожидаемого поведения; приоритеты, зависимости и критерии исправления). Затем отдельная сверка с кодом ещё шестью проходами: доверие и mihomo API, лимиты, жизненный цикл TUI, гонки подтверждения, отказ службы, повторная проверка каждого предложенного исправления. Результат — 25 записей: B01–B19 исходные, B20–B22 из первого аудита, B23–B25 из сверки. Это статический аудит: процессы не запускались, нагрузка и поведение на реальной системе не измерялись. Описание экранов и задачи UI/UX — в [TUI-UI-UX.md](TUI-UI-UX.md); порядок работ и поправки к способу исправления — в [PLAN-0.2.7.md](PLAN-0.2.7.md).

**Приоритет:** P0 — риск безопасности либо удаления не той сущности; P1 — нарушение корректности, отказ или заметная потеря отзывчивости; P2 — деградация при большом объёме данных. Приоритет означает порядок исправления, а не результат динамического воспроизведения.

| Приоритет | Записи | Область |
|---|---|---|
| P0 | B01, B02, B07, B22 | границы доверия, подтверждение действия |
| P1 | B03–B06, B08, B10–B21, B23–B25 | ресурсы, ошибки, актуальность, отзывчивость, отказ службы |
| P2 | B09 | масштабирование списка зеркал |

Для каждого пункта ниже указаны условие, ожидаемая и фактическая логика, место, входящая и исходящая цепочки. Критерии закрытия сведены в [плане 0.2.7](PLAN-0.2.7.md).

## B01. Профиль подписки может добавить собственные сетевые listeners

- **Что:** YAML профиля Clash сохраняется как основа итогового конфига; ключ `listeners` не удаляется и не проверяется по allowlist. Созданный конфиг запускается службой mihomo без `User=`, то есть от root.
- **Где:** `src/vpn.rs:913–939, 941–949`; генерация службы `src/main.rs:1233–1239`.
- **При каких условиях:** активная HTTPS-подписка отдаёт YAML с дополнительным listener, например привязанным к `0.0.0.0`; служба запускается.
- **Ожидаемая логика:** из подписки переносятся только разрешённые поля, пользовательские listeners не могут обходить `vpn_allow_lan`; служба получает только необходимые привилегии для TUN.
- **Факт:** произвольные поля mapping остаются в `m`, кроме небольшого списка удаляемых ключей. `allow-lan` перезаписывается, но `listeners` — нет. При `vpn_dns = 0` ключ `dns` подписки тоже остаётся. Не удаляются `skip-auth-prefixes`, `external-controller-cors`, `hosts`, `sniffer`, `iptables`, `ebpf`, `authentication`. `bind-address` всегда выставляется в `*`. `proxy-providers` и `rule-providers` сохраняются вместе с `type: file` и произвольным `path`. Mihomo получает итоговый YAML и работает от root. Разбор YAML происходит до фильтрации ключей.
- **Зависит от:** `upd vpn start` → `vpn::prepare` → `vpn::write_config` → `vpn::build_config` → сохранённый YAML.
- **Кто зависит от:** `vpn::build_config` → `/var/lib/upd/vpn/config.yaml` → systemd `upd-vpn.service` → mihomo → сетевой listener.

## B02. Bearer-секрет отправляется на TCP-порт, который может занять другой пользователь

- **Что:** API клиент отправляет секрет в HTTP-заголовке на фиксированный TCP-адрес `127.0.0.1:9097`; перед запросом адресат не проверяется.
- **Где:** `src/vpn.rs:34, 1086–1090`; секрет создаётся и хранится в `src/vpn.rs` в функции `secret`.
- **При каких условиях:** mihomo остановлен, а локальный процесс успел привязать порт `9097`; затем `upd` вызывает VPN API.
- **Ожидаемая логика:** секрет не передаётся по TCP. API mihomo доступен только через Unix-сокет в каталоге `0700`; TCP-контроллер при этом не включается. У mihomo запрос через Unix-сокет не проверяет Bearer, поэтому граница доступа — права каталога и сокета, а не заголовок.
- **Факт:** обычное TCP-соединение уходит первому слушателю на loopback-порту; `Authorization: Bearer …` отправляется до получения ответа. Код специально удаляет из подписки `external-controller-unix` и записывает TCP `external-controller`.
- **Зависит от:** TUI или `upd vpn` → VPN-операция → `vpn::api` → ureq Agent → TCP `127.0.0.1:9097`.
- **Кто зависит от:** `vpn::api` → HTTP Authorization → локальный слушатель порта → секрет из `/etc/upd/vpn` → VPN-команды от имени root.

## B03. Размер распакованного архива mihomo не ограничен

- **Что:** ограничение применяется к скачанному gzip, но распаковка целиком накапливает результат в `Vec<u8>` без предельного размера.
- **Где:** `src/vpn.rs:1404–1425`, особенно `1418–1422`.
- **При каких условиях:** сжатый архив размером до установленного лимита содержит сильно расширяющиеся данные.
- **Ожидаемая логика:** распаковка прекращается при достижении максимального допустимого размера бинарника, до записи файла.
- **Факт:** SHA-256 проверяет только сжатые байты; `GzDecoder::read_to_end` продолжает выделять память до конца распакованного потока.
- **Зависит от:** `upd vpn core update` или `upd vpn prepare` → `vpn::core_install` → `read_progress` → проверка digest → GzDecoder.
- **Кто зависит от:** GzDecoder → `bin: Vec<u8>` → `atomic_write` → `/var/lib/upd/vpn/bin/mihomo` → systemd VPN-служба.

<a id="b04"></a>
## B04. Повторное нажатие `r` оставляет предыдущие потоки сбора состояния без контроля

- **Что:** каждый вызов `reload` создаёт новый detached thread. В `self.rx` сохраняется только последний receiver; замена receiver не отменяет предыдущий поток.
- **Где:** `src/tui.rs:237–245, 547–550`; завершение/опрос результата — `src/tui.rs:249–253`.
- **При каких условиях:** пользователь несколько раз нажимает `r`, пока `gather_status` предыдущих запросов не закончился.
- **Ожидаемая логика:** для сбора состояния существует не более одного активного задания; новый запрос ждёт или заменяет старый с его отменой.
- **Факт:** каждый запрос вызывает `thread::spawn`; старые сборы продолжают сканирование `/proc` и вызовы backend, а TUI теряет их receiver.
- **Зависит от:** клавиша `r` → `key_menu` → `App::reload` → `thread::spawn` → `gather_status`.
- **Кто зависит от:** `gather_status` → backend и `/proc` → detached thread → системные CPU, память и процессы `upd`.

<a id="b05"></a>
## B05. Поиск AUR можно запускать повторно до завершения предыдущего

- **Что:** `aur_start` всегда создаёт поток и заменяет сохранённый receiver; предшествующий поиск не отменяется.
- **Где:** `src/tui.rs:706–715, 878–898`; сетевой запрос и проверка установленных версий — `src/extras.rs:259–276`.
- **При каких условиях:** пользователь запускает новый поиск, пока предыдущий AUR HTTP-запрос или `pacman -Q` ещё выполняется. Тот же шаблон используется для проверки AUR на экране состояния (`src/tui.rs:458–479`).
- **Ожидаемая логика:** один активный поиск/запрос проверки каждого типа; предыдущая работа отменяется или новый запрос не запускается.
- **Факт:** новый `Receiver` затирает старый, но его поток и сетевой/пакетный вызовы продолжают выполняться.
- **Зависит от:** экран AUR → `key_input` → `aur_start` → `extras::aur_search` → HTTP и `installed_versions`.
- **Кто зависит от:** `aur_search` → detached thread → AUR RPC и `pacman -Q` → CPU, сеть и память процесса `upd`.

<a id="b06"></a>
## B06. Поток чтения PTY может пережить экран завершённой команды

- **Что:** reader thread блокируется на `read` копии master PTY. `Drop` посылает SIGHUP группе только если `exit_code` ещё не установлен.
- **Где:** `src/tui/process.rs:75–109, 147–157, 394–400`; удаление сессии с экрана — `src/tui.rs:370–378`.
- **При каких условиях:** главная команда завершается, её потомок остаётся жить и сохраняет открытый PTY; затем пользователь закрывает экран процесса.
- **Ожидаемая логика:** закрытие сессии прекращает reader thread и закрывает все оставшиеся дескрипторы/потомков этой сессии.
- **Факт:** после фиксации `exit_code` `Drop` не посылает сигнал группе; reader thread остаётся на блокирующем чтении, удерживая свой PTY-дескриптор. `finished()` считает команду завершённой через секунду после выхода лидера, даже если `read_done` ещё ложен, поэтому экран уже можно закрыть. `try_wait` к этому моменту успевает пожать процесс, и повторный `kill` по тому же pid был бы уже небезопасен.
- **Зависит от:** `App::exec` → `ProcessSession::spawn` → reader thread → `reader.read`.
- **Кто зависит от:** завершившаяся команда → `ProcessSession::poll` → `Drop` → незакрытый PTY потомка → detached reader thread и файловый дескриптор.

<a id="b07"></a>
## B07. EOF на stdin принимается за ответ по умолчанию

- **Что:** `confirm` возвращает `default_yes`, если `read_line` вернул EOF или ошибку чтения.
- **Где:** `src/common.rs:535–547`; подтверждение установки обновлений — `src/main.rs:483–494`.
- **При каких условиях:** `upd update` выполняется без интерактивного stdin (например, stdin закрыт), а до этого дошёл запрос с `default_yes = true`.
- **Ожидаемая логика:** без полученного ответа `confirm` возвращает отказ, независимо от `default_yes`. Пустой Enter по-прежнему означает ответ по умолчанию. Неинтерактивное обновление идёт через `upd auto`, а не через закрытый stdin у `upd update`.
- **Факт:** EOF и ошибка чтения дают `read_line` длиной 0, и функция возвращает `default_yes`. При `true` это касается не только установки: новостей, продолжения без снапшота, перезапуска служб, установки AUR-помощника и снятия алиаса. Ветка `upd vpn start` при EOF уже отменяет ожидание FlClash — `confirm` ведёт себя иначе.
- **Зависит от:** `upd update` и другие команды → `confirm(..., true)` → `stdin.read_line`.
- **Кто зависит от:** `confirm` → ветка установки → `Backend::upgrade` → пакетный менеджер → изменение установленных пакетов.

## B08. Верхние границы настроек потоков, повторов и времени не заданы

- **Что:** числовые параметры ограничиваются снизу, но не сверху. Число потоков зеркал может вырасти до числа кандидатов; число кандидатов включает все строки `mirror` и списки backend.
- **Где:** разбор настроек `src/common.rs:197–209`; кандидаты `src/mirrors.rs:231–249`; запуск workers `src/mirrors.rs:203–215`.
- **При каких условиях:** в `/etc/upd.conf` указаны большие `parallel`, `parallel_vpn`, `retries`, `timeout`, `rescan_count` или большой список зеркал.
- **Ожидаемая логика:** настройки имеют верхние пределы, согласованные с числом потоков и длительностью фоновой задачи.
- **Факт:** `Config::load` применяет только `max(minimum)`, а `measure` запускает до `min(parallel, jobs)` OS threads через `thread::spawn`, который при отказе ОС паникует. `download` использует `retries` как число итераций. Верхней границы нет и у `timeout`, `keep`, `extra_from_list`, `rescan_count`, `min_free_gb`, `vpn_sub_update_h`, `vpn_core_check_h`, `mirror_max_age_h`. Произведение часов на 3600 — отдельное переполнение, см. [B25](#b25).
- **Зависит от:** `/etc/upd.conf` → `Config::load` → `cmd_auto/check` → `check_mirrors` → `measure`.
- **Кто зависит от:** `measure` → `thread::spawn` на каждый worker → сетевые запросы → файловые дескрипторы и память процесса → системная задача обновления.

<a id="b09"></a>
## B09. Удаление дубликатов зеркал использует квадратичный проход

- **Что:** для каждого нового адреса `candidates` линейно перебирает весь уже собранный список.
- **Где:** `src/mirrors.rs:231–249`, строка `235`.
- **При каких условиях:** конфигурация или системный список содержит много различных зеркал.
- **Ожидаемая логика:** уникальность проверяется структурой с близкой к O(1) проверкой членства либо список ограничивается до дедупликации.
- **Факт:** при N различных адресах число сравнений растёт как N²; верхней границы для числа `mirror` в конфиге нет.
- **Зависит от:** `/etc/upd.conf` и backend → `candidates` → повторный `r.iter().any(...)` → сравнение нормализованных URL.
- **Кто зависит от:** `candidates` → `check_mirrors`/`rescan` → `cmd_auto`, `cmd_update` или `upd mirrors check` → длительность задачи и удержание общей блокировки.

<a id="b10"></a>
## B10. Постоянные ошибки зеркал повторяются последовательно

- **Что:** все неуспешные кандидаты источников `config`/`pinned` попадают в повторный проход, в том числе ошибки HTTP, которые повторный запрос не исправит. Повторный проход запускается с `parallel = 1`.
- **Где:** `src/mirrors.rs:252–260, 288–309`; таймаут запроса — `src/mirrors.rs:113–178`.
- **При каких условиях:** много вручную заданных/закреплённых зеркал недоступны или отвечают постоянной ошибкой.
- **Ожидаемая логика:** повторяются только временные сбои; повторный проход ограничен по числу адресов и не блокирует остальные операции на сумму всех таймаутов.
- **Факт:** условие для `config` и `pinned` истинно для любого `!ok`; каждый такой запрос повторяется отдельно последовательно с тем же timeout.
- **Зависит от:** `check_mirrors` → `mirror_needs_retry` → `retry: Vec<Job>` → `measure(retry, 1, ...)` → последовательные HTTP-запросы.
- **Кто зависит от:** `measure` → `check_mirrors` → `with_lock` для `auto/update/mirrors check` → ожидание общей блокировки → другие задачи `upd`.

<a id="b11"></a>
## B11. Вывод внешних команд целиком помещается в память

- **Что:** общий helper `out` использует `Command::output`, а затем создаёт `String` из полного stdout. Вызовы не задают лимит объёма.
- **Где:** `src/common.rs:477–482`; пример потребителя — `src/backend.rs:1275–1292`.
- **При каких условиях:** пакетный менеджер или другой дочерний процесс выдаёт очень большой stdout.
- **Ожидаемая логика:** ограничивать объём вывода либо разбирать поток построчно, сохраняя только нужные записи.
- **Факт:** весь stdout накапливается в `Vec<u8>`, после чего копируется/преобразуется в `String` до разбора.
- **Зависит от:** `cmd_check/update` или TUI reload → `gather`/`gather_status` → `Backend` → `common::out` → `Command::output`.
- **Кто зависит от:** `Command::output` → буфер stdout → `String` и parsed update list → состояние `upd` → пиковое потребление памяти.

<a id="b12"></a>
## B12. Ответы ряда сетевых API читаются до EOF без лимита размера

- **Что:** часть HTTP клиентов превращает весь ответ в `String` без ограничения байтов; таймаут соединения не задаёт верхний объём тела.
- **Где:** AUR `src/extras.rs:259–267`; RSS `src/extras.rs:429–436`; API релизов `src/vpn.rs:1370–1373`; список зеркал Arch `src/backend.rs:504–512`; ответы локального API mihomo `src/vpn.rs:1085–1108`; список зеркал Ubuntu `src/backend.rs:1117–1129`.
- **При каких условиях:** upstream или прокси возвращает необычно большой ответ и продолжает передавать данные до конца HTTP timeout.
- **Ожидаемая логика:** у каждого HTTP endpoint есть максимальный размер тела до разбора ответа.
- **Факт:** `into_string()` читает ответ целиком; общий лимит тела на этих вызовах не задан.
- **Зависит от:** `upd aur search`/`upd news`/`upd vpn core`/подбор зеркал/операция VPN API → HTTP клиент соответствующего модуля → `into_string`.
- **Кто зависит от:** HTTP response reader → полный `String` → JSON/XML parser → векторы результатов → память процесса `upd`.

<a id="b13"></a>
## B13. Ручная настройка позволяет занять порт контроллера портом прокси

- **Что:** фиксированный API controller занимает `127.0.0.1:9097`, но ручное значение `vpn_port=9097` принимается при разборе `/etc/upd.conf`.
- **Где:** `src/common.rs:227`; оба значения попадают в YAML в `src/vpn.rs:941–949`; документация запрещает этот порт: `docs/CONFIGURATION.md`.
- **При каких условиях:** администратор задаёт `vpn_port = 9097` вручную.
- **Ожидаемая логика:** загрузчик отклоняет или исправляет значение, конфликтующее с API controller.
- **Факт:** загрузчик проверяет только диапазон `1..=65535`; затем один и тот же TCP-порт назначается mixed proxy и external controller.
- **Зависит от:** `/etc/upd.conf` → `Config::load` → `vpn::build_config` → YAML `mixed-port` и `external-controller`.
- **Кто зависит от:** итоговый YAML → `mihomo -t` в `vpn::prepare` → `ExecStartPre` → `upd-vpn.service` → запуск VPN.

<a id="b14"></a>
## B14. Таймаут загрузки ядра больше таймаута старта systemd-службы

- **Что:** запрос core asset может длиться до 600 секунд, а VPN-служба ограничивает весь startup пятью минутами.
- **Где:** `src/vpn.rs:227–234, 1404–1419, 1778–1789`; `src/main.rs:1235–1239` (`TimeoutStartSec=5min`).
- **При каких условиях:** systemd запускает VPN, ядро ещё не установлено, и загрузка идёт медленно, но не простаивает дольше read timeout.
- **Ожидаемая логика:** лимит systemd покрывает максимальное время `ExecStartPre` либо подготовка ядра выполняется отдельной задачей до старта службы.
- **Факт:** `ExecStartPre=upd vpn prepare` может ждать HTTP запрос до 600 секунд; systemd завершает startup по истечении 300 секунд.
- **Зависит от:** systemd `upd-vpn.service` → `ExecStartPre` → `vpn::prepare` → `fetch_missing` → `core_install`.
- **Кто зависит от:** `core_install` → HTTP download → длительность подготовки → systemd startup timeout → запуск или отказ запуска mihomo.

<a id="b15"></a>
## B15. Счётчики трафика подписки складываются и умножаются без защиты от переполнения

- **Что:** значения `upload`, `download` и `total` поступают из HTTP-заголовка подписки, а сравнение 90% и форматирование используют обычные сложение/умножение `u64`.
- **Где:** разбор заголовка `src/vpn.rs:424–435`; вывод `src/main.rs:965`; уведомление `src/main.rs:1151–1157`.
- **При каких условиях:** ответ сервера подписки содержит счётчики, близкие к пределу `u64`.
- **Ожидаемая логика:** счётчики читаются как целые байты; переполнение явно обрабатывается; объём и сравнение доли остаются корректными для любого принятого значения.
- **Факт:** заголовок сначала парсится как `f64`, затем приводится к `u64`. Целые больше 2^53 уже теряют точность, а слишком большое значение насыщается до `u64::MAX`. После этого `(upload + download) * 10` и `total * 9` выполняются без `checked_*`; то же сложение есть в `fmt_bytes` статуса. Переполнение искажает долю либо вызывает panic при включённых overflow checks.
- **Зависит от:** ответ подписки → `fetch_sub` → `parse_userinfo` → сохранённый `SubInfo` → `vpn::load_state`.
- **Кто зависит от:** `SubInfo` → `vpn status` и `cmd_notify` → форматирование трафика → уведомление о почти исчерпанном лимите.

## B16. После ошибки нового поиска AUR на экране остаются результаты предыдущего запроса

- **Что:** обработчик ошибки меняет строку состояния, но не очищает `self.aur.list`; таблица и панель описания продолжают показывать старые пакеты.
- **Где:** обработка результата `src/tui.rs:717–728`; отображение и установка выбранного результата `src/tui.rs:744–748, 755–795`.
- **При каких условиях:** выполнить успешный поиск, затем запустить другой запрос, который завершается ошибкой HTTP или разбора ответа.
- **Ожидаемая логика:** при новом поиске старый список не выдаётся за результат нового запроса; при ошибке показываются ошибка и явное пустое/предыдущее состояние с подписью.
- **Факт:** `aur_start` обновляет запрос и состояние, не очищая список; ветка `Err` в `aur_poll` присваивает только `status`. `draw_aur` рисует оставшийся список, а Enter запускает установку выделенного в нём пакета.
- **Зависит от:** экран AUR → `key_aur` → поле запроса → `aur_start` → `extras::aur_search`.
- **Кто зависит от:** ошибка `aur_search` → ветка `Err` в `aur_poll` → старый `aur.list` → `draw_aur` → `key_aur` запускает `upd aur install` для старой строки.

## B17. Экран VPN синхронно проверяет процессы и службу при каждой перерисовке

- **Что:** TUI перерисовывает экран в цикле с опросом клавиатуры до 200 мс, а `draw_vpn` при каждом проходе читает состояние подписок и сканирует `/proc`. Если VPN выключен, вызывается `systemctl is-active`; на вкладке настроек `vpn_opts` повторно читает конфигурацию, правила, состояние службы, состояние VPN и geo-файлы.
- **Где:** цикл и перерисовка `src/tui.rs:247–276`; вызовы в `draw_vpn` `src/tui.rs:1437–1467`; `vpn_opts` `src/tui.rs:1192–1202`; обход `/proc` `src/vpn.rs:1283–1292`; `unit_state` `src/common.rs:941–945`.
- **При каких условиях:** TUI открыт на любой вкладке VPN; дополнительные обращения к `systemctl` происходят при выключенной службе и на вкладке настроек.
- **Ожидаемая логика:** медленные/системные данные собираются в фоне с интервалом, кэшируются до следующего обновления и не читаются заново в каждом `draw`.
- **Факт:** `flclash_running` обходит каталоги `/proc` и читает `comm` процессов на каждом кадре; `unit_state` запускает дочерний `systemctl` через `Command::output`; конфигурационные файлы читаются повторно из функции формирования строк настроек.
- **Зависит от:** TUI → `main_loop` → `term.draw` → `draw_vpn` → `flclash_warning`/`vpn_opts` → `/proc`, файлы и `systemctl`.
- **Кто зависит от:** `draw_vpn` → повторные файловые чтения и обход `/proc` → запуск `systemctl` при условиях выше → задержка кадра и лишняя системная работа во время показа VPN.

## B18. Часть операций TUI выполняет блокирующий ввод-вывод в обработчике клавиши

- **Что:** некоторые действия вызывают команды ОС, сетевые/API операции или сканирование файлов прямо в основном цикле событий, а не через фоновую задачу/экран процесса.
- **Где:** загрузка списка снимков `src/tui.rs:625–629` и `src/extras.rs:507–545`; применение зеркал `src/tui.rs:834–841`; применение параметров VPN `src/tui.rs:1233–1245` и вызовы из `key_vpn_opts` `src/tui.rs:1370–1429`; цикл `src/tui.rs:247–276`.
- **При каких условиях:** команда `snapper`/`timeshift`, применение зеркал, VPN API или системная команда выполняется медленно либо ждёт ответа.
- **Ожидаемая логика:** длительная операция работает в фоне, экран показывает ход/ожидание, а ввод остаётся отзывчивым; либо операция запускается в существующем Process screen.
- **Факт:** обработчик клавиши не возвращается в `main_loop`, пока синхронный вызов не завершится; за это время TUI не рисует новый кадр и не опрашивает клавиатуру.
- **Зависит от:** клавиша/выбор меню → `key` или `activate` → синхронная функция действия → `Command::output`, файловая операция либо VPN API.
- **Кто зависит от:** медленная операция → блокирующий обработчик → `main_loop` не доходит до следующей отрисовки/опроса событий → TUI не реагирует на ввод до возврата.

## B19. Экран состояния не обновляет снимок после открытия

- **Что:** экран состояния показывает объект `Status`, полученный при запуске TUI или последнем `reload`; клавиша `r` обрабатывается только на главном меню.
- **Где:** начальная загрузка `src/tui.rs:191–196`; обновление и горячая клавиша меню `src/tui.rs:237–245, 541–554`; обработчик экрана состояния `src/tui.rs:508–519`; сбор полей `src/main.rs:1000–1031`.
- **При каких условиях:** пока TUI открыт, система меняется вне него (например, VPN-служба, таймер, конфигурационные файлы или обновления), затем пользователь открывает/продолжает смотреть `i · Состояние` без возврата на меню и нажатия `r`.
- **Ожидаемая логика:** при открытии страницы или явном действии обновления собирается новый `Status`, а время этого снимка видно пользователю.
- **Факт:** переход на `Screen::Status` только сбрасывает прокрутку; экран отображает прежний `self.st`. В обработчике Status клавиши `r` нет.
- **Зависит от:** `gather_status` → `App::reload` → сохранённый `self.st` → меню `i` → `draw` экрана Status.
- **Кто зависит от:** экран Status → `status_lines(&self.st)` → сведения о службах/VPN/сети/снапшотах → решение пользователя на основе сохранённого снимка.

## B20. Экран зеркал повторно собирает системные данные на каждом кадре

- **Что:** отрисовка управляемых зеркал повторно загружает конфигурацию и сохранённые замеры, читает сетевые маршруты и MAC, перечитывает список закреплённых зеркал и заново строит/сортирует кандидатов. Цикл вызывает `draw` после каждого ожидания ввода длительностью до 200 мс.
- **Где:** `src/tui.rs:247–276, 1048–1108`, `src/tui.rs:799–812`; `src/common.rs:685–729`, `src/mirrors.rs:231–249`.
- **При каких условиях:** TUI оставлен на странице зеркал, особенно при большом списке кандидатов или медленном доступе к системным файлам.
- **Ожидаемая логика:** системный снимок и строки таблицы собираются по событию входа/обновления/изменения настройки; `draw` использует готовые данные.
- **Факт:** `draw_mirrors` выполняет перечисленные чтения и сортировку на каждом кадре; `mirror_rows` снова вызывает `candidates` и линейное сопоставление с замерами.
- **Зависит от:** `main_loop` → `term.draw` → `draw_mirrors` → `cfg`/`mirror_state`/`fingerprint`/`pinned`/`mirror_rows`.
- **Кто зависит от:** файловые чтения и пересборка → длительность кадра → отзывчивость страницы зеркал; большой список усиливает [B09](#b09).

<a id="b21"></a>
## B21. Разрыв канала фоновой задачи оставляет экран в ожидании без восстановления

- **Что:** обработчики сбора общего статуса, поиска AUR, VPN snapshot и замера задержек принимают только `Ok` из `try_recv`; `Disconnected` обрабатывается так же, как «результат ещё не готов».
- **Где:** `src/tui.rs:249–253, 717–728, 1163–1189`.
- **При каких условиях:** соответствующий worker завершается без отправки результата, например после panic или ошибки до `send`; для общего статуса достаточно `backend::detect()` с `Err`.
- **Ожидаемая логика:** разрыв канала завершает состояние загрузки, показывает ошибку и разрешает повторную попытку.
- **Факт:** receiver остаётся в состоянии экрана. В AUR сохраняется «ищу в AUR...», VPN не запускает новый snapshot, пока `v.rx` остаётся `Some`; общий статус при первом запуске остаётся без данных до ручного повторного `r`. Проверка AUR на экране «Что доступно» уже отличает `Disconnected` от «ещё не готово»; этот путь не нужно переписывать, его нужно сохранить.
- **Зависит от:** `reload`/`aur_start`/`vpn_poll`/замер задержки → `thread::spawn` → закрытие sender без сообщения → `try_recv`.
- **Кто зависит от:** оставшийся `Some(receiver)` → индикатор ожидания или условие `v.rx.is_none()` → отсутствие ошибки и автоматического восстановления.

## B22. Подтверждение удаления VPN-подписки привязано к индексу, а не к записи

- **Что:** первое нажатие удаления запоминает номер выбранной строки. Второе отправляет CLI тот же номер, предварительно считав список заново; между нажатиями подписки может изменить другой процесс.
- **Где:** `src/tui.rs:1335–1355`; разрешение номера и изменение списка под блокировкой — `src/vpn.rs:667–679`.
- **При каких условиях:** после первого `x` другой экземпляр `upd` удаляет подписку перед выбранной строкой или иначе меняет порядок; затем пользователь нажимает `x` повторно.
- **Ожидаемая логика:** подтверждается неизменяемый ID конкретной подписки; если записи с этим ID уже нет, операция отменяется. Проверка ID и удаление выполняются атомарно. Активация (`use`) тоже адресует ID. Имя для этого недостаточно: после санитизации оно может совпасть.
- **Факт:** `confirm_del` содержит только `usize`; второе нажатие сравнивает индекс и вызывает `upd vpn del N`. CLI удаляет запись, которая теперь находится под этим номером. Enter активирует подписку тем же номером через `use_sub`. В публичном `SubPub` поля `id` нет, хотя у `Sub` стабильный `id` уже есть.
- **Зависит от:** экран VPN → вкладка подписок → `key_vpn_subs` → `confirm_del` → повторное `x` или Enter → `upd vpn del N` / `upd vpn use N`.
- **Кто зависит от:** изменение списка между нажатиями → разрешение `N` в `delete_sub` или `use_sub` → удаление или активация другой подписки. Удаление последней оставшейся записи ещё и останавливает VPN.

## B23. Якоря YAML в профиле подписки разворачиваются без бюджета

- **Что:** тело подписки ограничено 32 МБ, но затем целиком передаётся в `serde_yaml` 0.9. Библиотека разворачивает якоря и алиасы без предела числа узлов. Фильтрация ключей в `build_config` выполняется только после успешного разбора.
- **Где:** чтение тела `src/vpn.rs:466`; классификация `src/vpn.rs:617–623`; повторный разбор `src/vpn.rs:918–922`.
- **При каких условиях:** HTTPS-подписка отдаёт YAML с алиасами, который укладывается в лимит сырого тела и заставляет парсер построить дерево много больше исходного размера.
- **Ожидаемая логика:** разбор отказывает при превышении бюджета узлов, глубины или числа алиасов, до сборки конфига и до запуска mihomo. Лимит сырых байтов этот случай не закрывает.
- **Факт:** `classify_sub` и `build_config` вызывают `serde_yaml::from_str` на всём документе. Ошибка памяти возникает в процессе `upd`, в том числе от root в `prepare`.
- **Зависит от:** `upd vpn add` / `update` / `prepare` → `fetch_sub` или чтение профиля → `serde_yaml::from_str`.
- **Кто зависит от:** разбор → память процесса `upd` → добавление подписки, сборка конфига и `ExecStartPre`.

<a id="b24"></a>
## B24. Любой локальный процесс с именем FlClashCore блокирует запуск VPN

- **Что:** признак конфликта с FlClash — строка `comm` процесса, равная `FlClashCore`. При таком процессе `prepare`, `start` и `restart` завершаются ошибкой. `comm` задаёт сам процесс: достаточно скопировать исполняемый файл под этим именем или вызвать `prctl(PR_SET_NAME)`.
- **Где:** `src/vpn.rs:1283–1292`; отказ запуска `src/vpn.rs:1226–1231`, `1239–1244`, `1779–1782`. Поиск портов для запасного прокси использует тот же признак: `src/vpn.rs:369–387`.
- **При каких условиях:** непривилегированный пользователь запускает процесс с этим `comm`, пока служба VPN стартует или перезапускается. Процессу не нужны TUN и слушающий порт.
- **Ожидаемая логика:** запуск блокируется только при реальном конфликте: чужой TUN или слушатель на порту прокси/DNS. Имя процесса само по себе службу не останавливает.
- **Факт:** `flclash_running` возвращает предупреждение на первом совпадении `comm`. `prepare` превращает его в ошибку `ExecStartPre`, и `upd-vpn.service` не стартует. Тот же обход `/proc` TUI делает на каждом кадре VPN.
- **Зависит от:** `systemctl start upd-vpn` → `ExecStartPre` → `vpn::prepare` → `flclash_running` → `/proc/*/comm`.
- **Кто зависит от:** ложное совпадение → отказ `prepare`/`start`/`restart` → VPN не поднимается, пока процесс жив.

<a id="b25"></a>
## B25. Интервал подписки и часовые настройки переполняют умножение на 3600

- **Что:** интервал из заголовка `profile-update-interval` сохраняется как `i64` без верхней границы. Срок следующей проверки считается умножением на 3600. То же умножение применяется к `vpn_core_check_h` и `mirror_max_age_h`.
- **Где:** разбор заголовка `src/vpn.rs:447–448`; сравнение `src/vpn.rs:701–702`; ядро `src/vpn.rs:1823`; зеркала `src/main.rs:282`, `367`. Верхняя граница часов в `Config::load` не задаётся.
- **При каких условиях:** подписка присылает очень большой `profile-update-interval`, либо в конфиге указано слишком большое часовое значение.
- **Ожидаемая логика:** интервал ограничен диапазоном, в котором умножение на 3600 определено; сверхлимитное значение отклоняется или сжимается до максимума. Проверка срока не паникует и не меняет смысл из-за обертки.
- **Факт:** `h.max(1)` не ограничивает верх. В отладочной сборке переполнение `i64` паникует и обрывает `upd auto` или обновление подписок. В release-сборке умножение оборачивается, и подписка начинает обновляться каждый цикл либо, наоборот, никогда.
- **Зависит от:** ответ подписки или `/etc/upd.conf` → сохранение интервала → `update_subs_locked` / `maintain` / `cmd_auto`.
- **Кто зависит от:** переполнение → обрыв фонового обслуживания или неверный срок → пропущенное либо постоянное обновление подписки, ядра и зеркал.
