# Очередь Grok, 2026-10-06

Исполнитель: **Grok 4.7, reasoning high**. Объём только этот файл. Роль — **независимый рецензент** работы Composer 2.5, автор отрицательных fixtures **до** реализации рискованных подзадач, автор ADR и материалов по первичным источникам, по [MODEL-WORKFLOW](MODEL-WORKFLOW.md) §4. Grok не пишет продуктовый код и не принимает решения пользователя.

Источник требований: [REMAINING-DAG-PLAN-2026-10-06](REMAINING-DAG-PLAN-2026-10-06.md). Проверяемая очередь: [COMPOSER-QUEUE-2026-10-06](COMPOSER-QUEUE-2026-10-06.md). Контракт парсера: [I03-PARSER-IMPLEMENTATION-CONTRACT-2026-10-04](I03-PARSER-IMPLEMENTATION-CONTRACT-2026-10-04.md). Pinned ядро: mihomo `v1.19.32`, commit `88dcbf7f1614a67c3b36b848ee3592dfa92ada36`.

## Правила

- **Запись только в** `docs/design/cm-network-manager/grok-review/`. `src/`, `tests/`, `Cargo.*`, `cosmic/`, очереди и DAG не редактировать: это зона Composer и координатора. Контрпример оформляется текстом fixture в `grok-review/fixtures/`; переносит его в `tests/` Composer.
- Сборка и тесты — только с отдельным каталогом: `CARGO_TARGET_DIR=/tmp/cm-grok-target cargo test --offline --locked …`. Общий `target/` Composer не трогать.
- Сеть: только чтение публичных первичных источников pinned версии (`raw.githubusercontent.com/MetaCubeX/mihomo/<commit>/…`, документация crates). Реальные подписки, URL провайдеров, UUID, пароли и ключи не запрашивать и не использовать. Установка, службы, изменение сети хоста запрещены.
- Не выбирать варианты нерешённых вопросов (D4 и далее). D1–D3 решены пользователем 2026-10-06: [I03-DECISIONS-2026-10-06](I03-DECISIONS-2026-10-06.md); ревью проверяет реализацию строго по нему.
- Порядок чтения при ревью: задача в DAG и очереди Composer → контракт → diff (`git diff` и новые файлы) → raw evidence → только потом отчёт автора. Цель — найти failure scenario, а не подтвердить работу.
- Не коммитить.

### Формат ревью одной подзадачи

Файл `grok-review/R-<ID>.md`:

- **Вердикт:** `ACCEPT` / `REOPEN` / `BLOCKED` (не хватает входа).
- **Проверено:** revision или хеш diff, команды, фактический результат тестов (число, отказы).
- **Находки:** для каждой — серьёзность `P0` (утечка секрета, обход валидации, silent dropping, принятие того, что ядро отвергает) / `P1` (нарушение критерия «готово, когда», расхождение с pinned source) / `P2` (качество); `файл:строка`; конкретный вход → неверный результат; ссылка на строку первичного источника.
- **Не проверено:** что осталось вне ревью и почему.

`REOPEN` без воспроизводимого входа не ставить. Статус всех ревью ведётся в `grok-review/STATUS.md` (ID, вердикт, дата, revision).

## Протокол fixtures

Composer начинает `.b`, `.m`, `.o`, `.r`, `.t`, `.u` только после `FIXTURES_READY` в `grok-review/STATUS.md`. Поэтому fixtures идут в G1 с приоритетом: **`.b` нужен первым** — Composer дойдёт до него после `H.01`, `H.02`, `.a`.

- Каталог `grok-review/fixtures/<ID>/`: входные файлы (`*.yaml`, `*.json`, `*.txt` для URI) и `cases.md` — для каждого входа ожидаемый результат: «принять» с ожидаемым digest-инвариантом или «отказ» с ожидаемым классом ошибки (`UnsupportedField`, `UnsupportedFeature`, `Malformed`, лимит…). Точный код ошибки, если в контракте его ещё нет, — предложение, Composer сводит его к фиксированному набору и пишет, что изменил.
- Только синтетические данные: выдуманные хосты из `example.invalid`, ключи и UUID, сгенерированные для теста. Ни одного реального узла.
- Fixture должен бить в конкретный риск из чек-листа ниже, а не повторять позитивный случай.
- После выкладки записать в `STATUS.md`: `<ID> FIXTURES_READY <дата> <число случаев>`.

## G1.7 Отрицательные fixtures до реализации

`M` на каждый ID · L1 (тексты входов, не код) · формат — §Протокол fixtures

- **`G1.7.b` валидатор вложенных опций:** неизвестный вложенный ключ; один ключ дважды в разном регистре и дважды буквально; NUL, CR, LF, управляющие символы, bidi-символы в строке; строка ровно на лимите и на 1 байт больше; пустой список и список на лимите +1; вложенность на лимите +1; неверный тип в каждой позиции (строка вместо числа, map вместо списка, число вместо bool); две пары взаимоисключающих полей; парное поле без пары; два входа с разным порядком ключей и одинаковым ожидаемым digest.
- **`G1.7.m` WireGuard:** ключ не base64; base64 длиной 31 и 33 байта; `allowed-ips` с неверным CIDR; пересекающиеся peers; число peers на лимите +1; `amnezia-wg-option`, `dialer-proxy`, `remote-dns-resolve`, `dns` по отдельности — отказ, а не удаление; маркер-ключ (уникальная строка), по которому `.o` будет искать утечку.
- **`G1.7.o` секреты:** набор входов по всем протоколам с уникальными маркерами в каждом секретном поле (uuid, password, private-key, pre-shared-key, obfs-password, auth, токены), включая поля, которых нет в списке Composer; `cases.md` перечисляет, где маркер **не должен** встретиться (status DTO, `Debug`, тексты ошибок, diagnostic export, evidence).
- **`G1.7.r` URI:** percent-encoding в пароле, имени, path; IPv6 в квадратных скобках и без; порт 0, 65536, не число; повторяющийся query-параметр; неизвестный query-параметр; пустой fragment; `vmess://` с лишним полем JSON, с base64 без padding, с не-UTF-8; `ss://` в формате SIP002 и legacy base64, с plugin; схема в верхнем регистре; URI длиной на лимите +1; пары «URI ↔ native» с одинаковым ожидаемым digest для каждого протокола.
- **`G1.7.t` определение формата:** HTML-заглушка провайдера (синтетическая) → retry следующим UA; пустое тело; base64 от HTML; base64 от base64; YAML, который выглядит как список URI; JSON с BOM; тело на лимите +1; unsupported semantics → terminal отказ без retry.
- **`G1.7.y` пропуски и подтверждение:** подписка proxies+groups+rules (ожидание: `PendingConfirmation`, три имени секций); подтверждение с чужим digest; повторный refresh с тем же набором пропусков (публикуется без вопроса) и с новым классом (не публикуется); падение узлов на 51% и на 49%; 0 узлов после пропусков; старый Store без полей схемы (миграция); узлы `skip-cert-verify: true` без pin, с `fingerprint`, с `false`; маркеры секретов в пропущенных строках и секциях — не должны появиться в сводке.
- **`G1.7.u` ручной сервер:** секрет передан аргументом CLI → отказ; секрет из stdin и из файла с правами 0644 (ожидание по контракту — записать вопрос, если его нет); правка сервера → тот же Node ID, новое поколение; правка, меняющая протокол → новый Node ID.

- **`R-…r`:** для каждого протокола URI и native дают один digest; percent-encoding в пароле и имени; IPv6 в квадратных скобках; неизвестный query-параметр → отказ; `vmess://` с лишними полями JSON; `ss://` в обоих форматах; ошибки без эха URI.
- **`R-…y`:** миграция старого Store; `deny_unknown_fields` сохранён; сводка не содержит текста строк/URI/значений; `accept_omissions` привязан к digest сводки; три условия автообновления по [I03-DECISIONS](I03-DECISIONS-2026-10-06.md); `tls_verification` входит в digest узла.
- **`R-…q/.s/.t`:** реализация ровно по таблицам D1/D3 в [I03-DECISIONS](I03-DECISIONS-2026-10-06.md); `inline` proxy-providers дают узлы; 0 узлов → отказ; HTML-заглушка даёт retry следующим UA, а не terminal отказ; двойной base64; ни одного сетевого запроса к remote providers.
- **`R-…u`:** секрет не проходит через argv (проверить `/proc/self/cmdline` в тесте или по коду разбора); правка сервера сохраняет Node ID.
- **`R-…v/.w`:** удаление источника с активным профилем идёт через staged removal; при отсутствии бинарника mihomo статус `SKIPPED`, не `PASS`.
