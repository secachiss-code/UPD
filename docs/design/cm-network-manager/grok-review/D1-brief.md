# Материалы к D1: группы, правила, провайдеры

Статус: материал. Решение пользователя записано в [I03-DECISIONS-2026-10-06.md](../I03-DECISIONS-2026-10-06.md): вариант 2 сейчас, вариант 3 — задача I04. Дата материала: 2026-10-06. Пин ядра: mihomo `v1.19.32`, commit `88dcbf7f1614a67c3b36b848ee3592dfa92ada36`.

## Вопрос пользователю

Как импортировать native-подписку, в которой рядом с `proxies` лежат `proxy-groups`, `rules`, `sub-rules` или провайдеры: отвергать документ целиком, как парсер делает сейчас; принимать узлы и записывать в provenance имена пропущенных секций с подтверждением; или сохранять группы и правила типизированно для будущего генератора I04? Remote-провайдеры в любом случае не ходят в сеть, `file` не читает путь хоста, пока нет confined resolver. Открытым внутри этого вопроса остаётся только `inline`.

## Что делает pinned ядро

`parseProxies` сначала строит узлы из `proxies`, затем провайдеры из `proxy-providers`, затем группы из `proxy-groups`. Имена групп проверяются на циклы. В карту заранее кладутся `DIRECT`, `REJECT`, `REJECT-DROP`, `COMPATIBLE`, `PASS`, `PASS-RULE`. Если группы `GLOBAL` нет, ядро создаёт её само. Типы групп, которые парсер принимает: `url-test`, `select`, `fallback`, `load-balance`. Тип `relay` отвергается с текстом, что его заменили на `dialer-proxy`.

Источник: [`config.go` `parseProxies`](https://github.com/MetaCubeX/mihomo/blob/88dcbf7f1614a67c3b36b848ee3592dfa92ada36/config/config.go#L879), [`outboundgroup/parser.go`](https://github.com/MetaCubeX/mihomo/blob/88dcbf7f1614a67c3b36b848ee3592dfa92ada36/adapter/outboundgroup/parser.go#L188).

`parseRules` идёт по строкам `rules`. У строки должен быть тип, payload и цель. Цель — имя уже собранного proxy или, для `SUB-RULE`, имя из `sub-rules`. Имя rule set в строке должно существовать в `rule-providers`. Пустая цель — ошибка формата. Без `rules` этот разбор просто не вызывается на пустом списке: узлы в ядре остаются, политики маршрута из подписки нет.

Источник: [`config.go` `parseRules`](https://github.com/MetaCubeX/mihomo/blob/88dcbf7f1614a67c3b36b848ee3592dfa92ada36/config/config.go#L1097), `parseSubRules` там же выше.

Провайдеры. И `proxy-providers`, и `rule-providers` знают три vehicle: `file` (путь через `IsSafePath`), `http` (`NewHTTPVehicle` с URL, заголовками и лимитом размера), `inline` (payload в самом документе, без vehicle). Неизвестный `type` — ошибка. `http` — это сеть и кэш на диске ядра, не локальные узлы.

Источник: [`adapter/provider/parser.go`](https://github.com/MetaCubeX/mihomo/blob/88dcbf7f1614a67c3b36b848ee3592dfa92ada36/adapter/provider/parser.go#L79), [`rules/provider/parse.go`](https://github.com/MetaCubeX/mihomo/blob/88dcbf7f1614a67c3b36b848ee3592dfa92ada36/rules/provider/parse.go#L44).

## Что делает код сейчас

Новый парсер `parse_native` на любую из секций `proxy-groups`, `rules`, `sub-rules`, `proxy-providers`, `rule-providers` возвращает `ParserError::UnsupportedNativeSection` и не отдаёт узлы (`src/sources/parser/native.rs`). Это отказ документа, не тихое выкидывание секции.

Legacy `src/vpn.rs` `build_config_for` для clash-профиля оставляет как раз эти шесть ключей (`PROFILE_KEYS`) и дальше дописывает свои порты, TUN, DNS и правила. Для не-clash подписки сам собирает `proxy-providers` типа `file`, группу `select` с именем `Proxy` и правило `MATCH,Proxy`. Поверх любых правил подписки ставит пользовательские правила, при флагах — direct для LAN и RU, и `MATCH`, если его не было.

`SourceProvenance` хранит формат, время, digest тела, версию и commit ядра, origin и digest UA. Поля «какие секции не импортированы» нет. Структура с `deny_unknown_fields`.

Очередь `.q` уже фиксирует рамку, которую D1 не отменяет: remote `proxy-providers` / `rule-providers` — отказ без сетевого запроса; `file` — отказ, пока нет confined resolver; диагностика в provenance называет секции, не их содержимое. `inline` очередь оставляет решению D1.

## Варианты

1. Отказ документа, как сейчас. Пользователь не получает узлы, если в подписке есть группа или правило. Таких подписок большинство. Маршрут подписки не теряется по частям: его нет, потому что импорта нет. Запрет silent dropping не нарушается. Legacy `vpn.rs` при этом те же секции принимает, два импортёра расходятся. I04 из этого импорта группы не получит.

2. Импорт узлов, секции групп и правил не исполняются. В provenance остаётся список имён секций, которые не вошли, и импорт ждёт подтверждения. Содержимое секций в диагностику не пишется. Пользователь получает узлы и свой маршрут cm (группа `select` / `url-test` и `MATCH`, как уже делает `vpn.rs`), и не получает группы и правила издателя: выбор по странам, правила стриминга, свои `MATCH`. Silent dropping начинается в тот момент, когда список секций не сохранён или подтверждения нет: граф выглядит как полный импорт тела, хотя тело шире. Digest тела уже обязан совпадать с `content_digest`; список пропусков — отдельное поле, его в схеме provenance ещё нет.

3. Группы и правила сохраняются типизированно для I04. Узлы и политика издателя оба доходят до генератора. Silent dropping этих секций нет, если сохраняется всё, что ядро приняло бы, а неизвестное внутри секции по-прежнему ошибка, не выкидывание. Объём — типы групп `select` / `url-test` / `fallback` / `load-balance`, строки правил с проверкой цели, `sub-rules` и их циклы. `relay` ядро уже отвергает. Remote и `file` провайдеры этим вариантом не становятся разрешёнными: их по-прежнему режет рамка `.q`. `inline` здесь как раз хранится вместе с секцией, без сети и без пути хоста.

## Мнение рецензента, не решение

Вариант 1 честно падает, и из-за этого новый импорт не берёт обычную clash-подписку, хотя `vpn.rs` её уже собирает. Вариант 2 совпадает с тем, как cm и так накрывает маршрут своим `MATCH` и auto url-test, если пропуск записан и подтверждён. Вариант 3 нужен I04, когда генератор должен уметь политику издателя, а не только узлы; до этого он хранит данные, которые генератор ещё не читает.
