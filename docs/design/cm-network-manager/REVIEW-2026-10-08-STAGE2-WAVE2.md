## Найденные дефекты и исправления

### 1. F: конфиг хоста смешивал Store с legacy-подпиской (критично)

`overlay_store_nodes` накладывал узлы Store **поверх профиля активной legacy-подписки**. Из legacy оставались группы с явными списками узлов, правила, `sub-rules` и `rule-providers` другой подписки. Последствия:

- если имена узлов в legacy и Store различаются, группы legacy ссылаются на несуществующие узлы, `mihomo -t` отклоняет конфиг, и переключение никогда не проходит;
- в сценарии A/B/A (V.05) это одна и та же подписка, поэтому её группы совпадают по имени с группами legacy. Сборка падала с «имя группы издателя совпало»: так это закрепил тест `a_colliding_group_name_rejects_the_build`;
- без активной legacy-подписки `cm vpn use source:ID` отказывал с «нет подписки».

Тесты этого не видели: фикстура legacy и источник Store имели один и тот же узел `n1`.

**Исправление.** `store_profile` (`src/vpn/store_source.rs`) строит тело профиля только из Store: узлы, группы, правила, `sub-rules` и inline `rule-providers` издателя. `build_config_for` (`src/vpn/config.rs`) выбирает между `store_profile` и `legacy_profile` (прежний код вынесен без изменений). Всё остальное — CM-настройки, TUN, DNS, геоданные, правила пользователя и геоправила спереди, группа автовыбора — добавляет прежний генератор, как для legacy-профиля clash.

- Издатель без групп: одна группа `Proxy` (select по всем узлам), как у legacy для списка ссылок. Правила издателя без его `MATCH`, затем `MATCH,Proxy`.
- Издатель с группами: его группы и правила целиком, включая его `MATCH`. Отказ — только при имени служебной группы автовыбора.

Новые тесты (`tests/audit_v04_store.rs`):

- `legacy_sections_do_not_leak_into_a_store_build`;
- `a_publisher_group_named_like_the_legacy_one_is_accepted`;
- `a_store_source_needs_no_legacy_subscription`;
- `an_auto_group_name_rejects_the_build`;
- `host_build_from_another_feed_is_accepted_by_mihomo` (`mihomo -t`, legacy и Store — разные подписки, с группами, `url-test`, inline `rule-providers` и автовыбором).

### 2. G: inline rule-providers проверялись, но не попадали в config

`accept_publisher` принимал `RULE-SET,<inline>,…`, но `PublisherPolicy` не хранил сами провайдеры. Сгенерированный config ссылался на несуществующий провайдер, и `mihomo -t` его отклонил бы. Фикстура для `mihomo -t` в `audit_i04_policy` была без `rule-providers`.

**Исправление.** Поле `PublisherPolicy::rule_providers`; оно попадает в config worker и в профиль хоста. В фикстуру для `mihomo -t` добавлены inline-провайдер и `RULE-SET`.

### 3. G: в config worker правила пользователя CM оказывались после `MATCH` издателя

`merge_worker` ставил правила издателя, включая его `MATCH`, **перед** правилами генератора. Правила пользователя CM не срабатывали никогда.

**Исправление.** Порядок: правила генератора (пользователь CM), затем правила издателя, затем один `MATCH` (издателя, если он есть, иначе генератора). Добавлена проверка коллизии имени группы издателя с группой генератора (`ConfigError::InvalidRule`). Тест: `publisher_fixture_is_accepted_by_mihomo` проверяет порядок, `provider_groups_and_name_clashes_are_explicit` — коллизию.

### 4. G: группы с `use` принимались без проверки

Группа издателя с `use: [provider]` проходила, хотя `proxy-providers` издателя не импортируются (D1). Config ссылался бы на несуществующий провайдер.

**Исправление.** `use` в группе издателя — явная ошибка `PolicyError::UnsupportedProvider`, в парсере — `ParserError::PublisherProvider`. Разрешён `include-all-proxies` наравне с `include-all`.

### 5. E1: готовность объявлялась до того, как слушает порт worker

`start` возвращал `ApiReady`/`RouteReady`, как только отвечал API-сокет. mihomo поднимает контроллер раньше listener-а, поэтому арендованный порт `127.0.0.1` ещё отказывал в соединении. В gate это проявилось как плавающий отказ `audit_i04_e2` (`Connection refused`, 1 раз из 3–8 прогонов).

**Исправление.** `MihomoWorker::wait_listener`: после API ждать, пока порт принимает TCP. То же после `PUT /configs` в `reload`, потому что ядро перезапускает listener-ы.

### 6. E1 (тест): гонка после `kill -9`

`health` может вернуть `Down` по отказу API раньше, чем убитая группа процессов исчезнет. Тогда `start` законно отвечает `Conflict`. Тест теперь дожидается `!group_alive()` перед перезапуском.

## Принято без замечаний

- **E1:** путь сокета API задаёт только генератор из каталога instance. `external-controller-unix` во входном документе — `Forbidden`. Проверки peer и владельца сокета существуют в одном месте (`core/mihomo/api.rs`); `vpn/core.rs` вызывает их, а не копирует. GEO-правила для worker отклоняются.
- **F:**
  - `cm vpn store off` отказывает, пока выбран источник Store;
  - сборка с выключенным флагом и выбранным источником — ошибка, а не тихий возврат на legacy;
  - флаг меняется только от root, пункт TUI повторно запускает `cm vpn store`;
  - откат при отказе проверки или reload сохраняет прежний config байт в байт;
  - `Subs` без `deny_unknown_fields`, поэтому прежняя версия `cm` читает файл с новым полем;
  - запись в Store под флагом требует digest пропусков.
- **E2:** счётчики `/connections` совпадают с nft в пределах ±5%. Два worker и legacy работают одновременно с раздельным egress, остановка одного не затрагивает остальных.
- **H, X:** выводы опираются на замеры и команды, проверка сделана бинарником, а не по памяти.
