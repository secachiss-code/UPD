# ADR: путь данных хоста и выход ядра мимо туннеля хоста (I07.T01.a, I07.T01.b)

Статус: выбрано координатором 2026-10-10 по результатам лаборатории. Продуктовый VPN хоста (служба с `auto-route` ядра) этим решением не заменяется: новый путь включается отдельной командой и принимается на установленной системе.

Путь данных приложения описан в [ADR-PACKET-FLOW](ADR-PACKET-FLOW.md) и здесь не меняется.

## Решение

Туннель хоста — такой же worker, как туннель приложения: ядро под uid пользователя без привилегий, TUN заранее создаёт CM. Маршруты, правила и таблицу nftables ставит CM, а не ядро (`auto-route: false`).

```
ip rule (по возрастанию приоритета)
1000+i  iif cmv<i>h              → таблица 100+i   туннель приложения i (как раньше)
1900+k  oif <внешний k>          → main            сокеты, привязанные к внешнему интерфейсу
1950+j  from <адрес внешнего j>  → main            обратная проверка пути для их ответов
1990    все, кроме default       → main            локальные сети, veth и TUN самого CM
2000    все                      → таблица 90      default dev cmtunh
2001    все                      → таблица 91      default dev cmsink (приёмник)
```

- **Туннель.** Всё, что не нашло точного маршрута в `main`, уходит в `cmtunh`.
- **Блокировка при сбое.** Если маршрута в `cmtunh` нет, трафик уходит в `cmsink` — интерфейс `dummy`, который молча отбрасывает пакеты. Если ядро хоста убито, TUN остаётся (он постоянный), и пакеты пропадают в нём.
- **Выход ядра наружу.** Ядро каждого туннеля привязывает исходящие сокеты к внешнему интерфейсу (`tun.auto-detect-interface: true`, то есть `SO_BINDTODEVICE`; с Linux 5.7 привилегии для этого не нужны). Правило `oif` отправляет такие сокеты в `main`. Меток сокетов нет: `SO_MARK` требует `CAP_NET_ADMIN`, а ядро работает с пустым набором привилегий.
- **IPv6 хоста** в режиме туннеля заблокирован: те же правила для `ip -6`, но таблицы 90 нет, остаётся только приёмник.
- **DNS хоста.** Запрос на любой внешний адрес идёт в `cmtunh` и перехватывается ядром (`dns-hijack`). Запрос на DNS локальной сети шёл бы мимо туннеля, поэтому таблица `ip cm_host` в цепочке `output` перенаправляет порт 53 на адрес DNS туннеля. Исключение — адреса, которыми само ядро находит свой сервер (`1.1.1.1`, `8.8.8.8`).

Режим хоста — не граница изоляции. Процесс пользователя может сам привязать сокет к внешнему интерфейсу и выйти мимо туннеля. Так же ведёт себя нынешний VPN хоста (`strict-route: false`). Приложения в своих сетях этой возможности не имеют: внешнего интерфейса они не видят.

## Что найдено по дороге

- **`blackhole` в таблице блокировки хоста ломает туннели приложений.** Проверка обратного пути для ответа ядру приложения попадает в ту же таблицу и получает отказ. Маршрут в интерфейс `dummy` считается обычным маршрутом и проверку проходит. Поэтому приёмник — `dummy`, а не `blackhole`. В таблицах приложений (`100+i`) `blackhole` остаётся: туда попадает только трафик с veth своего приложения.
- **Строгий `rp_filter`** (значение 1) отбрасывает ответы ядру, если нет правила `from <адрес внешнего интерфейса>`. Правило ставится всегда, независимо от значения `rp_filter`.
- **Действующее значение `rp_filter`** интерфейса — максимум из `all` и своего. В новом netns `all` равно 0, а интерфейсы получают 2.
- **Смену внешнего интерфейса ядро отслеживает само**, правила `oif` и `from` обновляет CM.

## Фильтр пакетов (I07.T01.b)

CM пишет только свои таблицы nftables: `inet cm` (приложения) и `ip cm_host` (DNS хоста). Чужие таблицы он не читает и не меняет; политика цепочек — `accept`, поэтому правила docker, libvirt, firewalld и ufw продолжают действовать. Команда `nft` из пакета `nftables` обязательна; `iptables-nft` работает через тот же механизм ядра и с таблицами CM не пересекается.

| Система | Что известно |
|---|---|
| Arch и производные, обычный `resolv.conf` | это стенд лаборатории (Garuda): всё выше проверено в пространствах имён |
| systemd-resolved | **не проверено.** Его сокеты привязаны к интерфейсу, перенаправление DNAT для них не сработает: DNS не будет работать, пока resolved не получит адрес DNS туннеля на `cmtunh` (`resolvectl`) |
| firewalld | **не проверено.** Интерфейсы `cmv*` и `cmtun*` не входят ни в одну зону |
| NetworkManager | **не проверено.** Ожидание: устройства, созданные извне, он не настраивает |

## Что не проверено

- Сосуществование с нынешним VPN хоста (ядро с `auto-route`) и с чужими VPN. До проверки `host_apply` отказывает (`conflict`), если видит их правила.
- Всё из таблицы выше со словом «не проверено».
- Режим хоста `proxy`: сетевых правил он не ставит, охват трафика не полный по определению.
- Сон и пробуждение, смена сети Wi-Fi на настоящем адаптере.
