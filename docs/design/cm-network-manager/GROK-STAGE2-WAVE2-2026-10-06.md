## Правила (без исключений)

1. **Перед каждой сдачей — полный gate с ядром, EXIT=0:**
   `CARGO_TARGET_DIR=$HOME/.cache/cm-grok-target CM_TEST_MIHOMO=$HOME/.cache/cm-cores/mihomo/mihomo sh tests/check_audit.sh`.
   В выводе не должно быть `SKIPPED` для тестов с ядром.
2. **Не переформатировать существующие файлы.** Запрещены `cargo fmt` и `rustfmt` по старым файлам: `rustfmt src/main.rs` форматирует ещё и `tui.rs`, `tui/*`; `rustfmt src/vpn/mod.rs` — все `src/vpn/*.rs`. В diff существующего файла — только смысловые строки. rustfmt — только по своим **новым** файлам, которые добавляются в `rustfmt --check` в gate. Проверка перед сдачей: `git diff --stat` по существующим файлам не должен показывать сотни строк там, где поменяно несколько функций. Лишнее переформатирование — отказ при ревью.
3. Сборка только `--offline --locked`. Временные каталоги в тестах — `TempDirGuard`. Сборочный каталог — `~/.cache/cm-grok-target` (`/tmp` маленький).
4. Без установки, без `systemctl`, без изменений сети хоста и файлов legacy (`/etc/upd`, `/var/lib/upd`, `/etc/cm`, `~/.config/cm`). Сетевые проверки — только в harness (`unshare -rn`).
5. Ни секретов, ни настоящих подписок в фикстурах, ошибках, `Debug`, выводе и evidence. Неподдержанное — явная ошибка, не молчаливый пропуск.
6. Новый `unsafe` — только с `// SAFETY:` (gate проверяет).
7. Evidence — только `summary.json` в `stage2-evidence/<дата>/<пакет>/` (D8). SKIPPED и NOT_RUN не записываются как PASS.
8. Коммит — только по поручению пользователя. Без поручения сдача — отчёт и `summary.json`.
9. Если пункт не закрыт — так и писать: «открыто, причина».

### Пакет E1 — `I04.T04.c` жизненный цикл worker через API на unix-сокете (L, ★)

**Файл:** `src/core/mihomo/lifecycle.rs`; адаптер `MihomoWorker: CoreAdapter`.

- **start:** каталоги instance (`core::instance::InstanceRoot::create`), аренды порта и сокета (`core::leases`), config через `generate_config`, проверка `validate_file`, запуск ядра `-d <state> -f <config>`, ожидание `ApiReady`.
- **Сокет API добавляет только генератор.** `external-controller-unix` по-прежнему запрещён во входном документе (`HOST_LISTENER_KEYS`). Путь берётся только из каталога instance (права 0700), после `worker::generate` — так же, как сейчас добавляется `type: mixed`. Пользовательский ввод путь задать не может.
- **reload:** `PUT /configs` с новым файлом. Если проверка ядром не прошла, прежний config остаётся в силе.
- **health:** `/version`; delay — для выбранного узла.
- **stop:** завершение процесса, освобождение аренд, удаление сокета.
- Проверки peer и владельца сокета — те же, что в `src/vpn/core.rs` (`peer_uid`, `api`). Перенести или обобщить, не копировать вторую реализацию.
- **Геоданные.** Пока нет офлайн-доставки баз (`I05.T04.a`), генератор worker отклоняет правила `GEOIP` и `GEOSITE` (`ConfigError::InvalidRule`). Иначе ядро скачает базы мимо CM. Тест обязателен.
- **Готово, когда:**
  - на harness: `start → ApiReady → reload → stop`;
  - после `stop` нет процессов ядра (проверка по pid-группе), сокета и аренд;
  - отказ проверки при `reload` оставляет прежний config, worker продолжает работать;
  - падение ядра (kill -9) даёт явное состояние `Down`, без зависшей аренды после `reclaim_absent`.

### Пакет F — `V.04` `cm vpn use source:ID` за флагом (L)

Это первая видимая пользователю функция новой модели. Пользователь будет проверять её **руками на своём VPN**, поэтому критерии ниже — то, что он увидит.

**Флаг.** Настройка `vpn_store_source` в `cm.conf`: 0/1, по умолчанию **0**. При 0 всё ведёт себя ровно как сейчас. Общей команды настроек в CLI нет, поэтому:
- **CLI:** новая команда `cm vpn store on|off|status`, повышение прав — как у остальных команд `cm vpn`;
- **TUI:** пункт на вкладке «Настройки» экрана VPN (`vpn_opts`), через существующий `ConfigSet` helper.

Строки i18n — на 6 языков, плюс строка в `VPN_USAGE`.

**Запись в Store.** Сейчас `cm source import` без `--dry-run` отказывает. Под флагом разрешить запись:
- `cm source import --url-stdin|--url-file|--from-legacy N` (без `--dry-run`) — один источник через существующий pipeline (`create_accepted_source`);
- пропуски D1/D2/D3 требуют подтверждения, как решено в D1–D3: без подтверждения команда печатает сводку пропусков и digest (`pending_import_summary`) и ничего не пишет; повтор с `--accept-omissions <digest>` передаёт digest в `create_accepted_source`;
- без флага — прежний явный отказ.

**Переключение.** `cm vpn use source:ID`:
- **Конфиг хоста строится legacy-генератором (`build_config_for`), меняется только источник узлов:** вместо `proxy-providers` с файлом подписки — встроенные `proxies` из Store (через путь V.03 `generate_from_store` для узлов). TUN, DNS, геоданные, правила, группы и сохранённый выбор остаются как в legacy. Поэтому ограничение по геоданным здесь не возникает.
- Порядок: кандидат → `validate_candidate_body` → атомарная замена → `reload` → проверка health. При любой ошибке возвращается прежний config, и VPN продолжает работать на прежнем источнике.
- `cm vpn use N` (legacy) работает как раньше и возвращает хост на legacy-подписку.
- Источник с пропусками D1 (группы и правила издателя не перенесены до G) — предупреждение в выводе, а не молчание.
- `cm vpn` (состояние) и экран VPN в TUI показывают, откуда узлы: `источник Store <ID>` или legacy-подписка.

**Готово, когда:**
- Unit-тесты:
  - флаг 0 → поведение и файлы как раньше;
  - отказ проверки → прежний config байт в байт;
  - отказ reload → откат;
  - секреты не в выводе.
- **Сценарий пользователя** (записать в отчёт точными командами; Grok его не выполняет, у него нет root и настоящей подписки):
  ```
  cm vpn store on                             # включить флаг
  printf '%s\n' 'https://…' | sudo cm source import --url-stdin
  sudo cm source list                         # виден источник и число узлов
  sudo cm vpn use source:<ID>                 # VPN переключился, сайты открываются
  cm vpn                                      # состояние: источник Store <ID>
  sudo cm vpn use 1                           # обратно на legacy-подписку
  cm vpn store off                            # флаг выключен, всё как раньше
  ```
  и что пользователь должен увидеть на каждом шаге.

### Пакет E2 — `I04.T04.d` статистика и `I04.T05.a` два instance + legacy (S+M, ★)

- **`I04.T04.d`** (`src/core/mihomo/stats.rs`): трафик и соединения через API worker. Физический трафик и трафик TUN не суммируются. **Готово, когда:** на harness счётчики совпадают с захватом nft ±5%.
- **`I04.T05.a`:** два worker с разными узлами плюс `host-legacy` одновременно. **Готово, когда** на harness:
  - захват показывает раздельный egress (разные remote);
  - остановка одного worker не меняет второй и legacy (health, счётчики);
  - аренды не пересекаются.

### Пакет G — `I04.T04.f` группы и правила издателя (D1, вариант 3) (L)

**Файл:** `src/core/mihomo/policy.rs`.

- **Группы `proxy-groups`:** `select`, `url-test`, `fallback`, `load-balance`. `relay` — явный отказ, как в ядре.
- **Правила `rules`:** проверка, что цель существует. `sub-rules` — с проверкой циклов. Rule-providers — только `inline`.
- `GEOIP`/`GEOSITE` подчиняются тому же ограничению, что в E1.
- Повторный разбор из сохранённого сырого тела без новой загрузки.
- Генерация в config worker и в путь V.04.

**Готово, когда:**
- подписка-фикстура с группами и правилами издателя даёт config, принятый `mihomo -t`;
- пропуски D1 для групп и правил у такой подписки исчезают;
- цикл в `sub-rules`, цель-призрак и `relay` дают явные ошибки.

### Пакет H — `I04.T03.b` ADR владения TUN (M, после E1)

- **Эксперимент на harness:** (а) CM заранее создаёт persistent TUN с owner uid и передаёт его ядру; (б) ядро создаёт TUN само, без маршрутов.
- **Критерии сравнения:** права (`CAP_NET_ADMIN` у кого), восстановление после kill -9, MTU, IPv6.
- **Выход:** `ADR-TUN-OWNERSHIP.md` с числами и командами. **Готово, когда** выбран вариант, подтверждённый на harness.
