# ADR: путь данных туннеля приложения (I08.T01.b)

Статус: выбрано координатором 2026-10-10 по результатам лаборатории. Путь данных **хоста** (I07) этим решением не определяется.

## Решение

У приложения свой network namespace с единственным интерфейсом veth. Worker (ядро) остаётся в сети хоста и работает под uid пользователя без capabilities. TUN для него заранее создаёт CM ([ADR-TUN-OWNERSHIP](ADR-TUN-OWNERSHIP.md), вариант A).

```
netns cm-<i>                хост
┌──────────────┐      ┌───────────────────────────────────────────────┐
│ приложение   │      │ ip rule: iif cmv<i>h → таблица 100+i          │
│ cmv<i>n ─────┼──────┼─ cmv<i>h   таблица: default dev cmtun<i>      │
│ default via  │ veth │                     blackhole default metric 200
│ 10.213.<i>.1 │      │ cmtun<i> ── worker (uid пользователя) ── наружу│
└──────────────┘      └───────────────────────────────────────────────┘
```

- Трафик приложения попадает на хост через veth. Правило `iif` направляет его в отдельную таблицу, где единственный путь — TUN worker-а.
- В той же таблице стоит `blackhole default` с худшей метрикой. Если маршрут в TUN исчез, трафик отбрасывается и не попадает в основную таблицу.
- Таблица nftables `inet cm` разрешает veth только обмен со своим TUN и запрещает интерфейсам `cmv*` всё остальное. Политика цепочки — `accept`: чужой forwarding (docker, libvirt) не затрагивается.
- Цепочка `input` той же таблицы запрещает veth приложения обращаться к самому хосту (решение Q09, строгий вариант): службы хоста приложению недоступны ни по адресу veth, ни по другим адресам.
- NAT не нужен: исходящие соединения worker-а — обычные локальные сокеты хоста.

## Почему не worker внутри netns приложения

Worker и приложение работают под одним uid (uid пользователя). Отличить их трафик внутри общего netns можно только по cgroup или метке сокета:

- метка сокета (`SO_MARK`) требует `CAP_NET_ADMIN` у ядра, а оно работает без capabilities;
- правило `socket cgroupv2` в nftables требует, чтобы путь cgroup существовал в момент загрузки правила (проверено: `Error: Could not parse cgroupsv2 path`), то есть правило нельзя поставить заранее, до запуска worker-а. Это окно без защиты.

Вариант с правилом `iif` не зависит ни от uid, ни от cgroup: всё, что пришло с veth приложения, идёт только в его TUN.

## Лаборатория

Скрипт: [tools/packet_flow_lab.sh](tools/packet_flow_lab.sh). Запуск: `HOME_REAL=$HOME unshare -rn sh packet_flow_lab.sh <пустой каталог>`. Ядро mihomo 1.19.32, `stack: gvisor`, `auto-route: false`. «Интернет» — третий netns с HTTP-сервером на `198.51.100.2:8080`.

## Что найдено по дороге

- `fwd` — зарезервированное слово nftables: цепочка называется `forward`.
- `ip netns add` пишет в `/run/netns`. В harness без root нужен `unshare -rnm` и tmpfs на `/run`.
- `~/.curlrc` пользователя задаёт прокси `127.0.0.1:7890`; в проверках `curl` вызывается с `-q` и `--noproxy '*'`.

## Графическая сессия из сети приложения

Проверено на хосте в `unshare -rn` (сеть хоста не менялась): сокеты Wayland (`$XDG_RUNTIME_DIR/wayland-1`) и D-Bus (`/run/user/<uid>/bus`) — файловые, из другого сетевого пространства открываются. Абстрактный сокет X11 (`@/tmp/.X11-unix/X0`) привязан к сетевому пространству и отвечает `ECONNREFUSED`, но клиент X11 сам переходит на файловый `/tmp/.X11-unix/X0`: `xdpyinfo` получил ответ сервера.

## Что не проверено

- DNS через `dns-hijack` на TUN: в лаборатории запросы шли по IP. Проверка — ребро Z02 пакета.
- IPv6: в netns он выключается (`disable_ipv6=1`) при политике `Block`; путь IPv6 через TUN не проверялся.
- Взаимодействие с VPN хоста в режиме TUN (вложенность, outer egress) — I07.
- Системный стек TUN (`stack: system`): измерен только `gvisor`.
