# I01: проект миграции UPD → CM

Дата: 2026-10-03. Это проект будущей транзакции по D04 и Q20. Код переноса не входит в этот документ и в текущие исходники не добавляется. Guard C17 остаётся действующим отказом. I01.T04 — **NO-GO**. Проверки C07, C09, C10 в полном scope, C11, C15 и C16 остаются неисполненными, пока нет production-used executor.

Обновление 2026-10-04: сначала исправлена граница запуска C17a. Затем по прямому поручению пользователя реализован общий durable executor и opt-in manual policy 0.2.7 с `cm migration plan|apply|recover`, private backup, ownership и compensation. [Актуальная реализация и проверки](I01-MIGRATION-IMPLEMENTATION.md). Разделы ниже описывают исходный проект и прежние пробелы, а не отсутствие нового кода. Обычный guard сохраняется; полная Linux/systemd/root-CLI приёмка и остальные layouts ещё не закрыты.

Связанные тексты: [аудит](I01-SOURCE-AUDIT.md), [guard](I01-MIGRATION-GUARD.md), [baseline](I01-BASELINE-REPORT.md), [контракт](I01-TEST-CONTRACT.md).

## 1. Что уже делает код

`main()` при команде `install` вызывает `migration::preflight_install(Path::new("/"))` до `Config::load` и до сохранения конфига по умолчанию. `cmd_install()` первым действием вызывает `migrate_upd()`, который делает тот же preflight и возвращает `Ok(false)`. Прежние stop, disable, удаление hooks и rename из этой функции удалены.

`inventory_legacy` считает присутствующим известный путь, включая dangling symlink и mask. Symlink или не-каталог в предке и ошибка чтения дают отказ. Содержимое credentials не читается. Наличие пути не считается ownership: `/usr/bin/upd` может быть чужим и всё равно блокирует установку, файл остаётся на месте.

Переменные `CM_*` и `UPD_*` preflight не обходят. Корень production — только `/`.

## 2. Классы layout

Будущая транзакция обязана классифицировать layout до первой записи. Неизвестный, чужой и неоднозначный классы отклоняются целиком.

| Класс | Признак | Решение до проверки транзакции |
|---|---|---|
| Fresh | Ни одного известного legacy-пути, предки читаются, целевые пути CM не являются чужим symlink | Единственный класс, который текущий guard пропускает к install |
| Manual | Известные пути в `/usr/local`, `/etc/upd.conf`, `/var/lib/upd`, user units или cron | Отказ. Перенос не реализован |
| Package | Пакетные пути `/usr/bin/upd`, `/usr/lib` units, pacman/apt hooks, polkit | Отказ. Имя файла не даёт права останавливать или заменять unit |
| Split | Одновременно есть следы UPD и CM | Отказ. Конфликт не сливается автоматически |
| Unknown / foreign | Путь есть, владелец или эффективное содержимое unit не установлены; ошибка чтения; symlink в предке | Отказ. Файл не удаляется ради обхода |
| Home references | Ярлыки и panel entries в домашних каталогах | Текущий inventory их не ищет. Автоматический переход запрещён, удаление по имени запрещено |

Shell alias `upd` в Garuda не является legacy-следом и не должен становиться причиной миграции.

## 3. Persisted plan

Memory-only rollback не принимается: он не переживает обрыв процесса. Будущий executor, когда его отдельно разрешат, ведёт журнал на диске и умеет продолжить восстановление новым процессом.

Запись журнала до мутации шага содержит:

- поколения source и target: digest и список путей, не секреты;
- private backup credentials, конфига и назначений, с исходными owner, mode и типом файла;
- исходные enabled и active состояния служб, включая drop-ins;
- признак занятой legacy-операции и identification helper по владению, а не только по имени процесса;
- список entrypoint, которые план действительно меняет, отдельно от чужих файлов с похожим именем.

Шаг журнала имеет состояние `planned`, `applied` или `compensated`. Следующий шаг не начинается, пока предыдущий не записан. Обрыв на любом шаге, включая ошибки после переноса данных: binary, GUI, units, hooks, daemon-reload, enable и старт ядра, восстанавливает backup и исходные состояния служб. Невосстановимый шаг оставляет legacy-дерево нетронутым и помечает план failed. Частично появившиеся пути CM в этом случае входят в compensation, а не остаются вторым пустым состоянием.

Блокировка действует на legacy helper и на новые операции CM на всём протяжении плана. Один статусный GET не считается такой блокировкой. PID reuse не заменяет start time и ownership операции.

Переход entrypoint различен для manual и package. Package-owned файлы план не заменяет. Ручные desktop, applet и cron переводятся только если содержимое и владелец совпали с ожидаемым отпечатком. Несовпадение — отказ всего плана до записи. Повторный запуск на уже компенсированном или уже завершённом плане идемпотентен и не создаёт вторую копию credentials.

## 4. Сверка MIG-01…MIG-08

| ID | Сейчас | Остаётся для транзакции |
|---|---|---|
| MIG-01 | Мутации `migrate_upd()` удалены. `install` отказывает до load и save | Rollback и журнал не реализованы |
| MIG-02 | Известные manual binaries, desktop и icons блокируют install | Перевод входов и запрет второго пустого state не реализованы. Home references не инвентаризируются |
| MIG-03 | `disable --now` по имени удалён. Известные unit, drop-in и wants/requires links дают отказ | Эффективный unit и foreign override не различаются: оба только блокируют install |
| MIG-04 | `/etc/upd.conf` и `/etc/upd` входят в inventory и останавливают install до stop | Слияния двух конфигов нет и не должно происходить молча |
| MIG-05 | `/etc/cron.d/upd` блокирует install и не удаляется | Политика перевода cron не реализована |
| MIG-06 | Preflight не смотрит на env. `migrate_upd()` больше не возвращает успех из test mode, не выполнив проверку | Самой транзакции нет, поэтому env по-прежнему не является изоляцией будущего executor |
| MIG-07 | Присутствие `/run/upd/helper.sock` блокирует install | Занятость операции по ownership не проверяется. Отсутствие socket не доказывает простой |
| MIG-08 | Guard не смотрит целевые пути CM | Fresh symlink, чужой владелец и запись через подменённый target остаются открытыми. Отказ legacy-пути это не закрывает |

## 5. Пробел за пределами команды install

Preflight вызывается из `install` и из `cmd_install()`. Остальные команды доходят до `Config::load` без этой проверки.

`conf_path()` в `src/common.rs:44-46`: если `/etc/cm.conf` отсутствует и `/etc/upd.conf` существует, путём конфигурации выбран файл UPD. Сохранение отсутствующего файла в `main()` (`src/main.rs:97-98`) тогда не создаёт второй конфиг, потому что выбранный путь уже есть. Но команды, которые сами вызывают `Config::save`, пишут прямо в `/etc/upd.conf`. Уточнение 2026-10-04 по чтению кода: `cm lang КОД` (`src/main.rs:1617`), `cm mirrors add/del` (`:710`), переключение режимов VPN (`:940`, `:947`). Эти команды не исполнялись.

`state_dir()` в `src/common.rs:47-49`: если `/var/lib/cm` отсутствует и `/var/lib/upd` существует, каталогом состояния выбран каталог UPD.

`Config::save` (`src/common.rs:386-388`) до записи берёт два lock-а и создаёт их файлы. Первый — `.<имя conf>.lock` рядом с `conf_path()` (`:753-759`). Второй — `.vpn-config.lock` в `vpn::home()` = `state_dir()/vpn` (`src/vpn.rs:49-50`, `src/common.rs:717-722`); при отсутствии каталог создаётся с mode 0700. Поэтому при существующем `/var/lib/upd` любой `save()` пишет в `/var/lib/upd/vpn`, в защищённое C14 дерево UPD, даже если сам конфиг пишется в новый `/etc/cm.conf`.

На хосте 2026-10-04 есть `/etc/upd.conf`, `/var/lib/upd` и `/run/upd`, а `/etc/cm.conf` и `/var/lib/cm` отсутствуют. Отладочный `cm` под root хоста с командой, отличной от `install`, `help` и `version`, изменил бы данные UPD. Такой запуск запрещён до исправления. Исполнение пробела — сценарий W0-1 (= C17a) в [контракте волны 0](WAVE0-REVIEW-AND-TEST-CONTRACT.md), только в user/mount namespace с overlay.

Если `/etc/upd.conf` нет, а другой известный след есть, `install` получит отказ. Команда, которая не является `install`, при правах root и отсутствующем `/etc/cm.conf` доходит до сохранения нового `/etc/cm.conf`. При этом `state_dir()` может указывать на `/var/lib/upd`. Это не исполнялось. Для проекта это отдельный обязательный отрицательный сценарий: до появления транзакции такая команда не считается безопасным стартом рядом с UPD.

Чтение UPD-конфига через fallback не является переносом ownership и не означает, что CM принял установку.

## 6. Привязка к контракту

Существующие проверки покрывают будущий executor, когда его отдельно поручат. Сейчас все они для транзакции остаются NOT_RUN или BLOCKED, кроме уже исполненного отказа C08 и C17.

| Проектный шаг | Проверка |
|---|---|
| Перенос только old layout с backup и согласованными путями | C07 |
| Одновременные old и new остаются нетронутыми, отказ до stop | C08, уже PASS как отказ guard |
| Обрыв на каждом шаге журнала, восстановление новым процессом | C09 |
| Чужие units, hooks, desktop и binaries не заменяются по имени | C10 |
| Fresh target CM: symlink и чужой владелец отклоняются | Уточнение C10 в контракте, NOT_RUN |
| Повтор, приоритет env и запрет тихой смены credentials | C11 |
| Занятый helper и удержанные locks | C15 |
| CLI, desktop, applet, cron; чужие входы сохраняются | C16 |
| Home references не ищутся и не удаляются | Уточнение C16 в контракте, NOT_RUN |
| Не-install команда не создаёт CM config и не пишет в дерево UPD при legacy-следе | C17a = W0-1 K0–K6 в [контракте волны 0](WAVE0-REVIEW-AND-TEST-CONTRACT.md), NOT_RUN |

Новый удалённый сетевой контракт из этого проекта не следует. Уточнения C10, C16 и не-install записаны в [контракте](I01-TEST-CONTRACT.md) как будущие disposable-проверки, не как разрешение их исполнить в текущем задании.

## 7. Условие снятия guard

Guard снимается только для конкретного класса layout, после того как отдельный исполнитель получил PASS по C07–C11 и C15–C16, включая уточнения раздела 6, а независимая проверка приняла evidence. До этого Q20 закрыт отказом и резервной копией в проекте, не исполненным переносом. Явный rollback остаётся требованием, а не свойством текущего кода.
