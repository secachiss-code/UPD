# Контракт DATA-04 — Сохранять существующий конфиг при ошибке чтения?

**Предусловия:** исправление [fix/DATA-04](../fix/DATA-04.md) завершено; зависимости: —. Использовать собственный изолированный fixture.

## Подготовка входа

Изолированный UPD_CONF с контролируемой ошибкой read_to_string или невалидным UTF-8; проверить байты файла до и после команды сохранения.

**Наблюдаемая граница:** src/common.rs:144–151: Config::load возвращает defaults при любой ошибке read_to_string; src/main.rs:73–76 и многочисленные TUI/CLI ветки затем вызывают Config::save, переписывая /etc/upd.conf.

## Развилка принятия / корректности

1. **Положительная ветвь:** Отсутствующий файл в первый запуск получает defaults; существующий файл с I/O/UTF-8 ошибкой сохраняет исходные байты и выдаёт ошибку, даже при попытке изменить один параметр.
2. **Отрицательная ветвь:** Если операция после failed read перезаписывает старый /etc/upd.conf значениями defaults, контракт нарушен.
3. **Решение:** обе ветви совпали с ожиданием — контракт принят; любая не совпала — контракт отклонён с минимальным воспроизводимым входом и фактическим выводом; fixture не запустился — статус «не проверен».

## Что сохранить как доказательство

Записать команду адресного теста, ожидаемый/фактический exit status, состояние файлов/JSON и короткий вывод. Для условного эффекта отделять подтверждение кода от испытания на конкретной ОС или версии утилиты.

**После закрытия:** отметить контракт в [тестовом DAG](../TEST_DAG.md).
