# Контракт SEC-06 — Отказывать при ошибке создания секрета API?

**Предусловия:** исправление [fix/SEC-06](../fix/SEC-06.md) завершено; зависимости: —. Использовать собственный изолированный fixture.

## Подготовка входа

Вынести генератор случайных байт и запись секрета в инъецируемые зависимости; подать отказ каждого шага и проверить конфиг/API без реального mihomo.

**Наблюдаемая граница:** src/vpn.rs:449–460: буфер из нулей заполняется через /dev/urandom, Result игнорируется; сохранение secret тоже игнорируется. build_config:552 и api:691 вызывают secret() независимо.

## Развилка принятия / корректности

1. **Положительная ветвь:** При отказе генератора случайных байт или записи файла prepare/api возвращают ошибку и не создают рабочий конфиг с известным секретом; при успешной генерации повторный вызов читает тот же секрет.
2. **Отрицательная ветвь:** Если секрет из 16 нулевых байт используется либо API получает другой секрет после неудачной записи, контракт нарушен.
3. **Решение:** обе ветви совпали с ожиданием — контракт принят; любая не совпала — контракт отклонён с минимальным воспроизводимым входом и фактическим выводом; fixture не запустился — статус «не проверен».

## Что сохранить как доказательство

Записать команду адресного теста, ожидаемый/фактический exit status, состояние файлов/JSON и короткий вывод. Для условного эффекта отделять подтверждение кода от испытания на конкретной ОС или версии утилиты.

**После закрытия:** отметить контракт в [тестовом DAG](../TEST_DAG.md).
