# Контракт SEC-04B — Защитить сохранённый APT URI?

**Предусловия:** исправление [fix/SEC-04B](../fix/SEC-04B.md) завершено; зависимости: [SEC-04A](../test/SEC-04A.md). Использовать собственный изолированный fixture.

## Подготовка входа

Изолированное дерево APT в tmpdir с файлами разных mode/owner; ошибки записи вводить на каждом переходе через файловый адаптер. Сравнить байты и права до/после.

**Наблюдаемая граница:** src/backend.rs:528–554: fs::write(apt-original-uri) наследует umask процесса; URI может содержать credentials.

## Развилка принятия / корректности

1. **Положительная ветвь:** URI с credentials не читается непривилегированным пользователем и не теряется при успешном apply.
2. **Отрицательная ветвь:** Если право файла зависит от umask или ошибка записи замалчивается, контракт нарушен.
3. **Решение:** обе ветви совпали с ожиданием — контракт принят; любая не совпала — контракт отклонён с минимальным воспроизводимым входом и фактическим выводом; fixture не запустился — статус «не проверен».

## Что сохранить как доказательство

Записать команду адресного теста, ожидаемый/фактический exit status, состояние файлов/JSON и короткий вывод. Для условного эффекта отделять подтверждение кода от испытания на конкретной ОС или версии утилиты.

**После закрытия:** отметить контракт в [тестовом DAG](../TEST_DAG.md).
