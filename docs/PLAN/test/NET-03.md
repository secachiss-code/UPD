# Контракт NET-03 — Проверять короткий успешный ответ зеркала?

**Предусловия:** исправление [fix/NET-03](../fix/NET-03.md) завершено; зависимости: —. Использовать собственный изолированный fixture.

## Подготовка входа

Fake Backend и заглушки внешних команд с управляемыми stdout, stderr и exit status; сетевые ответы отдавать локальным сервером. Проверять и возвращаемое состояние, и код CLI.

**Наблюдаемая граница:** src/mirrors.rs:42–68: PROBE_MIN проверяется только при timeout; на EOF достаточно n>0. Backend::probe_url для apt может указывать на законный небольшой InRelease.

## Развилка принятия / корректности

1. **Положительная ветвь:** Короткий HTML 200 отвергается; корректный небольшой APT InRelease принимается; обрезанный относительно Content-Length ответ отвергается.
2. **Отрицательная ветвь:** Если HTML получает ok=true или корректный маленький файл отвергнут только из-за размера, контракт нарушен.
3. **Решение:** обе ветви совпали с ожиданием — контракт принят; любая не совпала — контракт отклонён с минимальным воспроизводимым входом и фактическим выводом; fixture не запустился — статус «не проверен».

## Что сохранить как доказательство

Записать команду адресного теста, ожидаемый/фактический exit status, состояние файлов/JSON и короткий вывод. Для условного эффекта отделять подтверждение кода от испытания на конкретной ОС или версии утилиты.
