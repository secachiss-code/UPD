# Архитектура cm 0.2.8

Этот документ описывает реализацию в исходниках, сценарии запуска и размещение системных данных. Логика собрана в библиотеку `cm` (`src/lib.rs`); бинарник `cm` (`src/main.rs`) — это CLI и TUI поверх неё. Отдельный крейт `cosmic/` (`cm-cosmic`) использует ту же библиотеку для индикатора COSMIC и запуска TUI, его описание — в [COSMIC-UI-UX.md](COSMIC-UI-UX.md).

## Модули

| Модуль | Ответственность |
|---|---|
| `lib.rs` | Библиотека: подключает модули ниже и общие для CLI, TUI и COSMIC типы. |
| `main.rs` | Бинарник: разбор CLI, повышение привилегий, порядок обновления, установка/удаление, генерация systemd-файлов, хуков и политики polkit. |
| `status.rs` | Полная сводка состояния (`gather_status`) для `cm status`, TUI и раздела «Обслуживание». |
| `summary.rs` | Снимок для панели из файлов и ограниченных probes; приоритеты значка и заголовка. |
| `helper.rs` | Помощник графического интерфейса `cm helper`: протокол JSON по Unix-сокету, проверка прав через polkit, одна долгая операция в PTY, клиент для интерфейса. |
| `common.rs`, `common/probe.rs` | Config и транзакции, JSON/atomic write, flock, bounded capture/deadlines/cancel, контекст UID, команды ОС и сведения о системе. |
| `backend.rs` | Trait `Backend` и адаптеры `Pacman`, `Apt`, `Rpm` для пакетных менеджеров. |
| `mirrors.rs` | Определение сети, кандидаты зеркал, параллельные пробы, оценка свежести и скорости, предзагрузка обновлений. |
| `extras.rs` | Flatpak, AUR (обновление, поиск через AUR RPC v5, установка через paru/yay), fwupd, новости Arch, snapper/timeshift, перезапуск служб. |
| `vpn.rs` | Подписки и профили, генерация YAML, REST-контроллер mihomo, ядро, геофайлы, systemd, системный прокси GNOME. |
| `tui.rs` | Группированное меню, экран состояния, просмотр списков, настройка зеркал, вкладки VPN, поиск в AUR и выбор языка. |
| `tui/process.rs` | PTY для интерактивных команд, потоковый журнал внутри TUI и переключение в полный терминал для полноэкранных программ. |
| `i18n.rs`, `i18n_table.rs` | Языки интерфейса и раскладки клавиатуры. |

### Переводы

Ключ перевода — русский текст в коде: `t!("текст")` и `t!("шаблон {} {1}", a, b)` вместо `format!`. Для русского строка возвращается как есть, для остальных языков берётся из таблицы `i18n_table.rs` (`[en, de, it, zh, ar]`; пустое значение — английский). Подстановки в шаблоне: `{}` по порядку, `{N}` по номеру, спецификаторы ширины и точности как в `format!`. Тест `every_source_key_is_translated` не даст добавить строку без перевода, `translations_keep_placeholders` сверяет число подстановок.

Системные идентификаторы не зависят от языка и записываются по-английски: описания systemd-юнитов, хуки pacman/apt, диспетчер NetworkManager, метки в mirrorlist, `/etc/garuda/garuda-update/config` и конфигах fish/bash, описания снапшотов (`cm: before update` / `cm: after update` — их показывает и GRUB, шрифт которого может не иметь нелатинских букв), имя группы автовыбора VPN в конфиге mihomo (`⚡ Auto`). Тест `install04_system_identifiers_do_not_depend_on_language` следит, чтобы туда не попала кириллица. Метки до 0.2.5 (русские) узнаются и при следующей записи заменяются.

Всё, что видит пользователь, — на языке интерфейса: имя группы автовыбора в TUI, `cm vpn` и цепочке серверов (`vpn::label`), описания снапшотов в списке cm, состояния systemd-юнитов (`unit_label`), шаблон `rules.txt` (создаётся на текущем языке; нетронутый русский шаблон прежних версий заменяется). В своих правилах группу автовыбора можно назвать на любом из языков или прежним `⚡ Авто` — в конфиг mihomo попадёт `⚡ Auto`.

Значения в `mirrors.json`, участвующие в логике (источник замера `config`/`pinned`/`search`/`list`, ошибки `timeout`, `dropped`, `lag N h` и т. п.), — тоже идентификаторы; переводятся только при показе (`i18n::tr_data`), прежние русские значения показываются так же. Начало сообщения о нехватке места («мало места») — отдельный ключ, по нему сообщение узнаётся.

Графический интерфейс собирается под glibc (wayland, GPU) в своём workspace `cosmic/` с libcosmic, закреплённым по ревизии; строки интерфейса переводятся той же таблицей `i18n_table.rs`, тест переводов читает и исходники `cosmic/src`.

Общие зависимости: `ureq` для HTTP, `serde`/`serde_json`/`serde_yaml` для состояния и профилей, `ratatui` для интерфейса, `libc` для системных вызовов и `sha2` для сверки релизного файла mihomo.

## Обновление и хранение состояния

`cm update` берёт блокировку `/var/lib/cm/.lock`, затем вызывает подбор зеркал и `mirrors::gather`. Сборщик обновляет пакетные индексы, получает списки системных пакетов и доступных интеграций, рассчитывает размер загрузки и записывает `updates.json`. Далее CLI предлагает прочитать новости Arch, загружает пакеты, делает снапшот, запускает транзакцию пакетного менеджера и выполняет послетранзакционные проверки.

`cm auto` использует ту же подсистему, но без интерактивной установки и проверки AUR. На батарее проверка выполняется, а предзагрузка обычно пропускается. В лимитной сети функция завершает фоновую задачу до обновления зеркал, VPN и списка обновлений. Штатный пропуск завершается с кодом `0` и сохраняет причину; сбой проверки пакетов, предзагрузки или записи состояния возвращает ненулевой код, который systemd фиксирует как неуспешный запуск.

Для Flatpak фоновая команда проверяет и предзагружает только system installation. Ручные `cm check` и `cm update`, запущенные через `sudo` или `doas`, дополнительно проверяют и обрабатывают per-user installation вызывающего пользователя.

Для pacman база синхронизации проверки находится отдельно от системной базы — `/var/lib/cm/syncdb`. Это позволяет получить список обновлений и сравнить его с установленными пакетами без изменения основной базы pacman. После транзакций pacman/apt установленные хуки вызывают `cm reconcile`, который повторно сравнивает список с сохранённым состоянием без сетевого запроса.

### Пакетные менеджеры

- **pacman**: временная sync-база, `pacman -Qu`, предзагрузка `-Sw`, обновление `-Syu`. На Garuda используется `garuda-update`; для Manjaro выбор зеркал остаётся за `pacman-mirrors`.
- **apt**: `apt-get update`, симуляция `full-upgrade`, загрузка через `apt-get -d`, установка через `apt full-upgrade`. Для зеркал редактируются источники основного архива и сохраняются их исходные версии.
- **dnf/dnf5/yum**: менеджер сам выбирает зеркала; загрузка выполняется в режиме download-only.
- **zypper**: менеджер сам выбирает зеркала; для Tumbleweed и Slowroll используется `dup`.

Выбор реализации выполняется по доступным командам в `PATH`, в порядке pacman, apt-get, zypper, dnf5/dnf/yum. Идентификатор системы берётся из `os-release`.

### Подбор зеркал

Источники кандидатов объединяются в порядке: пользовательский `mirror` из `/etc/cm.conf`, закреплённый блок пакетного менеджера, автоматически найденные либо первые зеркала из текущего списка. URL дедуплицируются за линейное время. Для каждого кандидата скачивается до 3 МиБ. Повторяются временные ошибки (таймаут, обрыв, отсутствие соединения, HTTP 429 и 5xx); повторный проход проверяет не более 16 адресов пулом до четырёх потоков и останавливается по общему бюджету времени.

Если backend предоставляет endpoint свежести, зеркала сравниваются по дате синхронизации. Скорость сглаживается экспоненциальным средним в статистике отпечатка сети. Лучшие результаты сохраняются в `/var/lib/cm/mirrors.json`; менеджер получает первые `keep` зеркал, а его прежний список остаётся запасным. История сетей старше 30 дней удаляется.

Отпечаток формируется из сетевого интерфейса, шлюза, MAC шлюза и имён обнаруженных TUN-интерфейсов. Проверка использует `/proc` и `/sys` и не делает внешний сетевой запрос.

## Службы, установка и упаковка

`cm install` размещает ручную установку в `/usr/local/bin` и `/etc/systemd`; пакетная — использует `/usr/bin` и `/usr/lib/systemd`. Пакетный сценарий установки вызывает `cm install --package`: он переносит остатки ручной установки и включает таймеры. Файлы генерирует `cm gen-files <каталог> <arch|deb|rpm>`.

В зависимости от системы создаются:

- `cm-auto.service` и `cm-auto.timer` — проверка и предзагрузка;
- `cm-net.service` и `cm-net.timer` — проверка смены сети;
- `cm-mirrors.path` и `cm-mirrors-apply.service` — возврат закреплённых зеркал после изменения mirrorlist Arch;
- `cm-notify.service` и пользовательский `cm-notify.timer`;
- `cm-helper.socket` и `cm-helper.service` — помощник графического интерфейса: сокет `/run/cm/helper.sock`, служба запускается по обращению и завершается без работы;
- `cm-vpn.service` — запуск mihomo от root с `ExecStartPre=cm vpn prepare`; права сужены до `CAP_NET_ADMIN`, `CAP_NET_RAW`, `CAP_NET_BIND_SERVICE`, `NoNewPrivileges`, `ProtectSystem=strict` с записью только в `/var/lib/cm/vpn`, `UMask=0077`. При обновлении cm (`cm install`, в том числе из пакетного сценария) работающая служба перезапускается без ожидания, чтобы подхватить новый unit и конфиг;
- pacman/apt hook для `reconcile` и dispatcher NetworkManager;
- политика polkit `/usr/share/polkit-1/actions/io.github.cm.policy` с действиями `status`, `check`, `vpn` (без пароля в активном сеансе) и `manage` (пароль администратора).

Ручная установка ставит и интерфейс COSMIC, если рядом с устанавливаемым бинарником лежит `cm-cosmic` (или `cm-cosmic-linux-amd64`): бинарник — в `/usr/local/bin`, `.desktop`-файлы и значки — в `/usr/local/share`. Пакетная установка ставит его отдельным пакетом `cm-cosmic`.

При отсутствии systemd ручная установка добавляет расписание в `/etc/cron.d/cm`, если cron-каталог существует. Удаление останавливает службы, снимает маркеры Garuda и просит backend вернуть исходные зеркала. Настройки VPN, подписки и общий каталог состояния намеренно сохраняются. На Garuda ручная установка с согласия пользователя снимает алиас `cm` → `garuda-update` в `~/.config/fish/config.fish` и `~/.bashrc` (строкой с пометкой после `source …garuda…`); удаление убирает только помеченные строки.

Сборка пакетов выполняется `package.sh`: он компилирует бинарник, запрашивает у него файлы установки для каждого формата, затем вызывает nfpm. Версия nfpm закреплена в скрипте; архив проверяется по опубликованному рядом списку SHA-256.

## VPN

`cm vpn add` загружает профиль и классифицирует его как Clash/mihomo YAML либо список URI. Адрес, индивидуальный User-Agent и профиль хранятся отдельно. YAML разбирается с бюджетом: число узлов и байт строк считается вместе с развёрнутыми алиасами, глубина и число алиасов ограничены. Заглушка «Приложение не поддерживается» отклоняется при загрузке и сборке конфига. Из профиля берутся `proxies`, `proxy-groups`, `rules`, `sub-rules`, `proxy-providers` и `rule-providers`. Каждый HTTP-provider получает относительный кэш в `providers/<тип>/<хеш источника>/`, с сохранением имени файла; идентификатор учитывает URL, имя, формат, behavior и заголовки авторизации. Это исключает пересечение кэшей при переключении подписок. Файловые ссылки на такой кэш перенаправляются вместе с ним; неоднозначные ссылки отклоняются. Остальные файловые provider-ы должны указывать существующий файл в разрешённом подкаталоге VPN; переход по symlink за пределы VPN home запрещён. Для inline-provider удаляется неиспользуемый `path`. Проверяются HTTP URL, формат/behavior и прямые ссылки `RULE-SET`/`use`. Абсолютные пути и компоненты `..` не допускаются.

`cm vpn doctor [N]` проверяет сохранённые профили и запускает `mihomo -t` для временных конфигов, не меняя активную подписку или рабочий `config.yaml`. Проверка ограничена 30 секундами; stdout/stderr ограничены, из ошибки выбирается конкретная причина вместо общей строки «test failed». Секреты узлов, age-ключи и значения HTTP-заголовков скрываются. Подготовка службы также проверяет временный конфиг до замены рабочего. Остальное задаёт `build_config`: порты, сокет контроллера, TUN, свой DNS, геофайлы, авто-группа и пользовательские правила.

Mihomo предоставляет API только через Unix-сокет `/var/lib/cm/vpn/mihomo.sock`; TCP-контроллера нет. Сам сокет mihomo создаёт с правами `0666`, поэтому доступ ограничивает каталог `0700`. Перед запросом `vpn::api` проверяет, что сокет и каталог принадлежат службе, каталог закрыт для группы и остальных, а `SO_PEERCRED` показывает uid службы. Ответ читается с пределом объёма. `vpn::snapshot` использует API для состояния групп, задержек и трафика. Переключение сервера закрывает старые соединения, чтобы выбор применился сразу.

При загрузке релизов сначала используется прямой запрос, затем локальный прокси работающего `cm-vpn`, а затем прокси-порт процесса `FlClashCore`, если этот процесс принадлежит root или пользователю, запустившему cm. Для первоначального `cm vpn start` недостающие ядро и геофайлы загружаются с видимым прогрессом. `ExecStartPre=cm vpn prepare` ничего не качает: проверяет порт, конфликт, наличие ядра, собирает конфиг и запускает `mihomo -t`. Конфликтом считается чужой TUN другого ядра VPN (FlClash, mihomo, clash, sing-box…) или занятый чужим процессом порт прокси либо DNS; имя процесса без TUN и порта запуску не мешает.

`cm auto` обновляет подписки по сроку и проверяет релизы FlClash/Mihomo. При появлении нового релиза FlClash скачивается подходящее ядро mihomo, сверяется обязательный SHA-256 digest из GitHub API, проверяется возможность запуска и затем файл атомарно заменяет прежнее ядро. При отсутствии digest установка отменяется. Геофайлы загружаются из релизов `MetaCubeX/meta-rules-dat`.

## Пути и права доступа

| Путь | Данные | Права, задаваемые приложением |
|---|---|---|
| `/etc/cm.conf` | Общая конфигурация и список предпочитаемых зеркал | `0644` |
| `/var/lib/cm/` | JSON-состояние, логическая блокировка, временная база pacman | Каталог `0755`, JSON `0644` |
| `/etc/cm/vpn/subs.json` | URL подписок, названия и состояние загрузки | Каталог `0700`, файл `0600` |
| `/etc/cm/vpn/rules.txt` | Пользовательские VPN-правила | Файл `0600` |
| `/var/lib/cm/vpn/` | Ядро, конфигурация, профили, геофайлы и сокет API `mihomo.sock` | Каталог `0700`; сгенерированный конфиг и профили `0600` |
| `/var/lib/cm/private/apt-*` | Оригинальные и применённые APT sources, их права и журнал восстановления транзакции | Каталог `0700`, файлы `0600` |
| `/etc/apt/cm-mirrors.list` | Список зеркал, используемый через `mirror+file:` | Файл `0644` |
| `/run/cm/helper.sock` | Сокет помощника графического интерфейса; права проверяются для каждого запроса через polkit | Сокет `0666` (создаёт systemd) |
| `~/.config/cm/cosmic.json` | Пользовательские настройки апплета (уведомления) | Файл пользователя |

Общие JSON-файлы не содержат URL подписок: для пользовательского VPN-состояния публикуются название, хост, срок, трафик и ошибки. Механизм установки использует root-права для системных пакетных транзакций, зеркал, systemd, TUN и прошивок.

## Ограничения и эксплуатационные заметки

- Приложение собирается как x86_64 Linux-бинарник; ядро VPN подбирается для уровня CPU x86_64 v1/v2/v3.
- Подписки принимают только HTTPS URL; перенаправления проверяются вручную, разрешены до пяти переходов только на HTTPS.
- При отсутствии SHA-256 digest в метаданных релиза mihomo установка отменяется.
- Сборка `package.sh` должна выполняться на Linux-системе, где `cm gen-files` может обнаружить один из поддерживаемых менеджеров пакетов.
- Фоновое состояние рассчитано на один системный экземпляр `/var/lib/cm`; тестовый/альтернативный каталог задаётся переменной `CM_STATE_DIR`.

## Разработка

Цель сборки и `CC` для musl задаются в `.cargo/config.toml`. Для локальной отладки действуют переопределения путей: `CM_CONF` (конфиг), `CM_STATE_DIR` (состояние), `CM_MIRRORLIST` и `CM_PACMAN_CONF` (файлы pacman), `CM_VPN_ETC` и `CM_VPN_HOME` (данные VPN). `CM_DEBUG=1` включает подробные сообщения проверки зеркал; `EDITOR` задаёт редактор пользовательских VPN-правил.

Для помощника: `CM_HELPER_SOCK` — путь сокета (клиент и сервер); в тестовом режиме `CM_HELPER_ALLOW=1` пропускает проверку polkit, а `CM_HELPER_EXE` подменяет запускаемую команду.

`CM_STATE_DIR` включает тестовый режим и отключает автоматический переход к root через sudo/doas. Используйте эту переменную только с изолированным состоянием для разработки и тестов; для обычного запуска её задавать не следует.

Основные команды сборки:

```sh
rustup target add x86_64-unknown-linux-musl
./build.sh
./package.sh
```

`build.sh` собирает и интерфейс COSMIC (`dist/cm-cosmic-linux-amd64`), если в системе есть заголовки wayland и xkbcommon; `CM_NO_GUI=1` отключает это. Отдельно: `cd cosmic && cargo build --release`.

Встроенные тесты расположены в модулях `src/*.rs`; тест TUI рендерит несколько экранов через `TestBackend`. Изменения конфигурации следует сверять с `Config::defaults`, `Config::load`, `Config::save` и текстом пользовательской документации.


## Контракты helper и GUI после аудита Luna 6

Протокол JSON имеет `protocol_version = 2` в Envelope/Reply/OperationEvent.
Клиент сначала отправляет Hello; несовпадение версии останавливает запрос до
мутации, без fallback. Каждый запуск получает уникальный operation_id, вопрос —
prompt_id. Input/Cancel относятся к конкретной операции; Input одноразовый.
Владелец и ID повторно проверяются после polkit. Replay имеет явную границу
ReplayComplete; старые callbacks не изменяют новую операцию.

Runner владеет Child, process group, PTY-input и reader. Ввод ограничен 1024
байтами и одной строкой без control characters, имеет deadline 1 s и очередь
16 команд; запись/ожидание выполняются вне State mutex. Echo отключается до
ввода. Cancel возвращает принятый/отклонённый результат; inline операции явно
сообщают Unsupported. При выходе leader PGID сразу очищается, drain ограничен
500 ms, reader пробуждается и join-ится до завершения runner.

До авторизации резервируются квоты 16 глобальных/8 на UID соединений. Полный
запрос: 64 KiB / 2 s. Event: 128 KiB, Reply: 20 MiB, запись: 2 s, replay: 3 s.
Строка/partial: 16 KiB; журнал: 5000 строк / 3 MiB; replay: 4 MiB;
subscriber: 256 событий / 4 MiB. Partial coalesces; overflow сообщает Gap и
закрывает подписку. Disconnect обнаруживается без нового вывода; RAII снимает
подписку/квоту. GUI использует bounded каналы и пробуждает socket-reader при
отмене stream.

Config сохраняется через уникальный exclusive temp, mode при создании,
fsync файла, rename и fsync каталога. Транзакция read-modify-write сериализуется
межпроцессным flock; старый снимок изменяет только свои поля, с merge зеркал.
Порядок блокировок и runtime-apply описан в
[AUDIT-LUNA6-LOCKS.md](AUDIT-LUNA6-LOCKS.md). UserContext берётся из peer UID/NSS
или явного CLI invoking user; daemon не меняет глобальное окружение. Фоновый
процесс без пользователя пропускает его sysproxy; ошибки применения видны.

`common/probe.rs` обслуживает stdout/stderr одним poll-loop, без reader threads.
Read-only probe имеет общий deadline 30 s, output budgets и cancel; отдельная
process group завершается и reap-ится на ошибке/timeout. Установка/AUR и команды,
ждущие пользователя, используют interactive policy, а не 30-секундный предел.

`cosmic/src/jobs.rs`: для каждого Kind максимум один фактический worker и одно
последнее отложенное задание. Поколения ключа/страницы отбрасывают старые ответы;
отмена future не освобождает слот, пока blocking worker не завершён. Состояния
Idle/Loading/Ready/Error, retries с backoff. I/O выполняется в spawn_blocking.
`cosmic/src/launch.rs`: один bounded reaper (256 children / 32 ошибок), без
ожидания child в UI; spawn/exit errors доступны интерфейсу.

## Свежие артефакты и воспроизводимые проверки

build.sh использует явные musl/GNU targets и --locked, уникальный staging и
logs. Версии свежих CLI/GUI сверяются через --version. `dist/build-manifest.tsv`
(либо CM_BUILD_MANIFEST) содержит результаты только текущего запуска; package.sh
использует собственный manifest/staging и не включает старый GUI при пропуске
его сборки. На ошибке выводится лог; посторонние файлы dist не удаляются.

`./tests/check_audit.sh` собирает обычные CLI/GUI бинарники (чтобы проверить production monomorphization), запускает core (musl), отдельный Cosmic (GNU), packaging
fixtures и проверки новых модулей. Нужны локальные Unix sockets/PTY. Полная
матрица: `CM_FULL_VISUAL=1 ./tests/check_audit.sh`; без неё Cosmic suite всё равно
рендерит два PNG smoke и проверяет encoder/decoder. Доказательства и ограничения:
[AUDIT-LUNA6-FINDINGS.md](AUDIT-LUNA6-FINDINGS.md),
[визуальная приёмка](audit-luna6-acceptance/README.md),
[ресурсные gates](audit-luna6-acceptance/RESOURCE-GATES.md).


Последующее [ревью исходной базы](AUDIT-LUNA6-PRIOR-REVIEW.md) уточнило TUI
lifecycle: Child/reader принадлежат ProcessSession, лидер наблюдается WNOWAIT
до cleanup группы и reap; завершённая сессия не держит reader. Nonblocking PTY
input имеет deadline 100 ms. COSMIC action notifications ограничены четырьмя
workers, ждут до 5 min с bounded capture; CLI notifications — до 30 s и не
помечают failure как доставленный. Ручной install бинарников использует тот же
unique/exclusive atomic_write (с однократным чтением install source в память).
